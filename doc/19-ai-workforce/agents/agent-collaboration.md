# Mianx.ai AI Agent Collaboration

> **This document defines the governed collaboration model for Humans, AI
> Agents, Teams, Departments, Products, Projects, Tenants, Customers,
> workflows, Tools, memory systems, reviewers, approvers, and auditors operating
> within the Mianx.ai Shared AI Workforce.**

---

# 1. Document Purpose

This document establishes the target-state standard for collaboration involving
Mianx.ai AI Agents.

It defines:

- collaboration purpose;
- collaboration principles;
- collaboration actors;
- Human-to-Agent collaboration;
- Agent-to-Human collaboration;
- Agent-to-Agent collaboration;
- Team collaboration;
- Department collaboration;
- cross-department collaboration;
- executive collaboration;
- Product collaboration;
- Project collaboration;
- Tenant collaboration;
- Customer collaboration;
- reviewer collaboration;
- approver collaboration;
- auditor collaboration;
- collaboration identities;
- collaboration sessions;
- messages;
- instructions;
- requests;
- responses;
- notifications;
- approvals;
- evidence;
- Task assignment;
- delegation;
- handoffs;
- context packages;
- memory sharing;
- Tool coordination;
- Model coordination;
- workflow coordination;
- orchestration coordination;
- separation of duties;
- conflict handling;
- deadlock handling;
- escalation;
- cancellation;
- timeouts;
- retries;
- partial failure;
- isolation;
- monitoring;
- suspension;
- quarantine;
- recovery;
- evidence;
- Production collaboration gates;
- current-state boundaries.

This document prevents:

- an Agent message from being treated as Human approval;
- a Task assignment from being treated as authority expansion;
- a delegation from exceeding the delegator’s authority;
- a handoff from losing ownership or evidence;
- one Agent from impersonating another Agent;
- one Agent from using another Agent’s credentials;
- one Project’s context from entering another Project’s collaboration;
- one Tenant’s information from entering another Tenant’s collaboration;
- an executive Agent from silently overriding Founder authority;
- Team consensus from replacing required Human approval;
- Agent-to-Agent messages from bypassing Governance;
- collaboration activity from being reported as verified outcomes.

This document does not independently:

- create a collaboration service;
- create a message bus;
- create a Team;
- create a Department;
- register an Agent;
- activate an Agent;
- grant delegation authority;
- grant Tool permissions;
- grant memory permissions;
- approve Customer communication;
- prove runtime collaboration;
- authorize Production collaboration.

The collaboration framework must make it possible to answer:

- Who initiated the collaboration?
- Which verified identity participated?
- Which Role did each participant perform?
- Which Agent Definition and Agent Instance participated?
- Which Product and Project applied?
- Which Tenant or Customer applied?
- Which environment applied?
- What objective was shared?
- Which Task was assigned?
- Which authority permitted the assignment?
- Was delegation involved?
- Which context was shared?
- Which memory was accessed?
- Which Tools were coordinated?
- Which approval was required?
- Which evidence was produced?
- Which participant owns the outcome?
- How were conflicts resolved?
- How was the collaboration suspended?
- What proves the final result?

# 5. Core Collaboration Principles

## 5.1 Every Participant Must Have a Verified Identity

Every material collaboration participant must be identifiable as:

- Human;
- Agent Definition;
- Agent Instance;
- Team;
- workflow;
- service;
- approved external system.

Anonymous material execution is prohibited.

---

## 5.2 Collaboration Does Not Expand Authority

A participant may not gain authority merely because another participant shares:

- a message;
- a Task;
- a context package;
- memory;
- Tool output;
- recommendation.

---

## 5.3 Human Approval Must Remain Human Approval

An Agent must not:

- fabricate Human approval;
- infer approval from silence;
- treat another Agent’s approval claim as Human approval;
- impersonate an approver.

---

## 5.4 Every Collaboration Must Have an Objective

Collaboration must be tied to:

- approved business need;
- Product outcome;
- Project outcome;
- Task;
- workflow;
- incident;
- evaluation;
- review;
- Governance activity.

---

## 5.5 Every Collaboration Must Be Scope-Bound

Collaboration must identify:

- Organization;
- Product;
- Project;
- Tenant;
- Customer;
- environment;
- region;
- Data classification;
- Risk;
- time period.

---

## 5.6 Least Privilege Applies to Collaboration

Participants receive only the context, memory, Tools, permissions, and Data
required for their approved contribution.

---

## 5.7 Ownership Must Remain Explicit

Every Task, decision, artifact, handoff, Risk, and approval must have an
accountable owner.

---

## 5.8 Handoffs Must Preserve Evidence

A handoff must not remove:

- original objective;
- scope;
- authority;
- limitations;
- failures;
- Risks;
- evidence;
- open decisions.

---

## 5.9 Failures Must Remain Visible

Collaboration must not hide:

- rejected work;
- failed Agent contributions;
- timeouts;
- conflicts;
- blocked approvals;
- unavailable Tools;
- missing evidence;
- residual Risks.

---

## 5.10 Shared Collaboration Does Not Mean Shared Confidential Context

Shared AI Workforce capability must preserve Product, Project, Tenant, and
Customer isolation.

---

## 5.11 Every Collaboration Must Be Suspendable

The system must support:

- participant suspension;
- channel suspension;
- Team suspension;
- workflow suspension;
- Product or Project suspension;
- Tenant suspension;
- Tool suspension;
- memory suspension;
- emergency cancellation.

---

## 5.12 Collaboration Claims Require Evidence

Documentation does not prove:

- active Teams;
- active Agent-to-Agent messaging;
- active delegation;
- runtime orchestration;
- context isolation;
- Production collaboration.

# 14. Agent-to-Agent Collaboration

Agent-to-Agent collaboration permits multiple approved Agent Instances to
contribute to one governed objective.

Every participating Agent must have:

- unique identity;
- approved Definition;
- valid lifecycle state;
- valid allocation;
- valid authority;
- valid permissions;
- approved Role;
- approved collaboration scope;
- approved communication channel;
- evidence obligations.

---

# 15. Agent-to-Agent Authentication

Before accepting a material message or Task from another Agent, the receiving
Agent should validate:

- sender Agent Instance ID;
- sender Definition ID;
- sender Role;
- sender lifecycle state;
- sender allocation;
- sender authority;
- sender Product scope;
- sender Project scope;
- sender Tenant scope;
- sender environment;
- message integrity;
- message expiry.

A sender’s display name is not sufficient identity proof.

---

# 16. Agent-to-Agent Authorization

A receiving Agent must not accept a Task merely because another Agent sent it.

It must validate:

- sender may assign or delegate the work;
- recipient Role permits the work;
- recipient Skills permit the work;
- recipient lifecycle state permits the work;
- recipient allocation permits the work;
- Product and Project scopes match;
- Tenant and Customer scopes match;
- environment is permitted;
- Risk is within ceiling;
- required approval exists.

---

# 18. Team Membership Rules

A participant may act as a Team member only when:

- membership is approved;
- Role is defined;
- allocation is valid;
- start date is valid;
- expiry or review date is defined;
- Product and Project scopes match;
- Tenant scope matches;
- required Skills are valid;
- permissions are current;
- no suspension applies.

Team membership does not grant every Team member the same permissions.

# 48. Prohibited Delegation

Delegation must not:

- transfer Founder authority;
- transfer constitutional authority;
- grant contract-signing authority to an Agent;
- grant fund-transfer authority to an Agent;
- remove Security controls;
- remove privacy controls;
- remove Product or Project isolation;
- remove Tenant isolation;
- permit self-approval;
- permit unlimited sub-delegation;
- continue after expiry;
- create unrestricted Production authority.

---

# 49. Sub-Delegation

Sub-delegation is permitted only when:

- original delegation explicitly allows it;
- maximum depth is defined;
- downstream recipients are eligible;
- scope becomes equal or narrower;
- expiry does not exceed the parent delegation;
- evidence remains traceable;
- original owner remains accountable.

# 53. Memory Sharing

- share secrets;
- share invalidated memory.

# 61. Approval Message Rules

- come from an authorized Human or approved authority;
- reference exact decision;

# 79. Collaboration States

| State | Meaning |
|---|---|
| `PROPOSED` | Collaboration need is documented |
| `VALIDATING` | Participants, authority, scope, and controls are checked |
| `APPROVAL-PENDING` | Required approval remains |
| `APPROVED` | Exact collaboration scope is approved |
| `SESSION-PENDING` | Collaboration session is being prepared |
| `ACTIVE` | Approved collaboration is underway |
| `WAITING` | Collaboration waits for dependency or response |
| `BLOCKED` | Collaboration cannot proceed |
| `REVIEW-PENDING` | Required review remains |
| `HANDOFF-PENDING` | Responsibility transfer remains incomplete |
| `SUSPENSION-PENDING` | Suspension is being enforced |
| `SUSPENDED` | New collaboration actions are blocked |
| `QUARANTINED` | Collaboration is isolated for investigation |
| `COMPLETED` | Defined collaboration activity concluded |
| `ACCEPTED` | Authorized owner accepted the outcome |
| `REJECTED` | Authorized owner rejected the outcome |
| `FAILED` | Required collaboration outcome was not achieved |
| `CANCELLED` | Authorized owner cancelled collaboration |
| `FINALIZED` | Final evidence and status are recorded |
| `ARCHIVED` | Historical record remains |

`COMPLETED` does not automatically mean `ACCEPTED`.
