# Mianx.ai AI Agent Performance

> **This document defines the governed performance model for Mianx.ai AI
> Agents. It separates activity, execution, quality, reliability, safety,
> Security, privacy, compliance, cost, capacity, utilization, latency,
> throughput, collaboration, evidence, Customer outcomes, and business outcomes
> so that activity volume or planned targets cannot be misrepresented as
> verified performance.**

---

This document establishes the target-state standard for defining, measuring,
reviewing, improving, restricting, suspending, and reporting AI Agent
performance.

- performance purpose;
- performance principles;
- performance ownership;
- performance identities;

# 5. Core Performance Principles

## 5.1 Performance Must Be Evidence-Based

A performance claim must reference:

- metric definition;
- measurement window;
- source Data;
- collection method;
- Agent identity;
- scope;
- environment;
- calculation;
- verifier;
- evidence.

---

## 5.2 Activity Is Not Performance

The number of:

- messages;
- Tasks accepted;
- Tool calls;
- tokens;
- generated files;
- hours active;

does not independently prove useful performance.

---

## 5.3 Completion Is Not Acceptance

An Agent may report work as completed while:

- review remains pending;
- acceptance remains pending;
- mandatory tests fail;
- evidence is incomplete;
- Customer outcome is unknown.

---

## 5.4 Quality Must Not Be Hidden by Volume

High output volume must not compensate for:

- fabricated evidence;
- Security failure;
- privacy violation;
- cross-Tenant leakage;
- critical quality failure;
- unauthorized action.

---

## 5.5 Safety Is a Hard Constraint

Critical safety, Security, privacy, legal, or Governance failure must not be
averaged away by positive performance elsewhere.

---

## 5.6 Measurement Must Be Scope-Aware

Performance must be attributable to:

- Agent Definition;
- Agent Instance;
- Role;
- capability;
- Skill;
- Product;
- Project;
- Tenant;
- Customer;
- environment;
- workflow;
- Task type;
- Model;
- Tool;
- measurement window.

---

## 5.7 Baselines Must Precede Targets

A target should normally be approved only after:

- instrumentation exists;
- Data quality is verified;
- baseline is measured;
- variability is understood;
- workload is classified;
- Risk is assessed.

---

## 5.8 Planned Values Must Be Labelled

Planned values must be labelled as:

```text
PROPOSED

NOT MEASURED

NOT APPROVED

NOT A RUNTIME RESULT
```

---

## 5.9 Failures Must Remain in the Denominator

Failed, rejected, timed-out, cancelled because of Agent fault, rolled-back, and
partially completed Tasks must not be excluded merely to improve performance.

---

## 5.10 Human Work Must Be Attributed

Human:

- corrections;
- reviews;
- interventions;
- approvals;
- recovery work;
- rework;

must be visible when evaluating Agent performance.

---

## 5.11 Cost Must Be Attributed

Performance must consider the cost of:

- Models;
- Tools;
- infrastructure;
- retries;
- failures;
- storage;
- review;
- support;
- recovery.

---

## 5.12 Performance Must Be Reproducible

A qualified reviewer should be able to reproduce the material calculation from
approved evidence.

---

## 5.13 Agents Must Not Score Themselves

An Agent may submit execution evidence.

It must not be the sole authority for:

- final score;
- target achievement;
- certification;
- Production promotion;
- Risk acceptance.

---

## 5.14 Performance Status Must Match Current Truth

Expired, disputed, invalidated, simulated, or incomplete Data must not be
reported as current verified performance.

A completion rate must define what counts as completed.

```text
Eligible Tasks

/

```

These rates must not be combined.

# 21. First-Pass Quality

First-pass quality should measure work accepted without material remediation.

```text
First-Pass Acceptance Rate
=
Outputs accepted without material rework
/
Outputs submitted for review
```

Minor formatting corrections should be distinguished from material rework.

---

# 22. Rework

Rework should classify:

```text
RW-0 — No Rework

RW-1 — Minor Formatting or Presentation

RW-2 — Minor Content Correction

RW-3 — Material Content Correction

RW-4 — Major Re-Implementation

RW-5 — Complete Rejection or Replacement
```

An Agent with high completion but high `RW-3` to `RW-5` rework is not
performing well.

---

# 23. Defect Severity

| Severity | Meaning |
|---|---|
| `D0` | No defect |
| `D1` | Cosmetic or minor presentation issue |
| `D2` | Minor functional or content issue |
| `D3` | Material quality issue |
| `D4` | Critical Security, privacy, legal, financial, or operational issue |
| `D5` | Catastrophic or enterprise-threatening issue |

D4 and D5 defects must act as hard-stop conditions.
