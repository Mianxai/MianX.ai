# Mianx.ai AI Agent Types

> **This document defines the governed classification system for every proposed,
> registered, provisioned, allocated, active, live-tested, and
> Production-controlled AI Agent operating within the Mianx.ai AI Workforce.**

---

# 1. Document Purpose

This document establishes the official target-state classification model for
Mianx.ai AI Agents.

It defines:

- what an AI Agent is;
- what an AI Agent is not;
- the difference between Roles, Capacity Seats, Agent Definitions, Agent
  Instances, Sessions, and Workers;
- hierarchy-based Agent classifications;
- functional Agent types;
- execution Agent types;
- advisory and decision-support Agent types;
- review and assurance Agent types;
- operational Agent types;
- Research Agent types;
- Customer-interaction Agent types;
- autonomy levels;
- Risk classifications;
- environment classifications;
- Product, Project, Tenant, and Customer scope;
- persistent and temporary Agent types;
- single-Agent and multi-Agent participation;
- Agent-type selection rules;
- registration requirements;
- evaluation requirements;
- Security restrictions;
- evidence requirements;
- prohibited Agent patterns;
- current-state boundaries.

This document is a classification authority.

It does not independently:

- approve an Agent Role;
- approve a Capacity Seat;
- create an Agent Definition;
- register an Agent Instance;
- provision an Agent;
- assign permissions;
- allocate an Agent;
- activate an Agent;
- authorize Production work;
- create runtime workers;
- prove runtime operation.

# 5. Core Agent Principles

## 5.1 Every Agent Must Have a Defined Purpose

An Agent must exist because of a verified business, Product, Project,
operational, Governance, or technical need.

Agent creation based only on an attractive title is prohibited.

---

## 5.2 Every Agent Must Implement an Approved Role

An Agent must reference an approved Role definition.

The Agent must not invent its own Role.

---

## 5.3 Every Agent Must Have Human Accountability

Every runtime Agent Instance must have one accountable Human owner.

An Agent cannot be its own accountable owner.

---

## 5.4 Every Agent Must Be Scope-Bound

Every Agent must operate within approved:

- Organization scope;
- Product scope;
- Project scope;
- Tenant scope;
- Customer scope;
- environment scope;
- Data scope;
- Tool scope;
- Model scope;
- financial scope;
- Risk scope.

---

## 5.5 Every Agent Must Use Least Privilege

An Agent must receive only the minimum permissions required for approved work.

Executive or senior titles do not grant unrestricted access.

---

## 5.6 Every Agent Must Remain Suspendable

Every operational Agent must support:

- restriction;
- suspension;
- credential revocation;
- Tool restriction;
- Model-route restriction;
- memory restriction;
- Task reassignment;
- retirement.

---

## 5.7 Every Agent Must Produce Evidence

Material work must produce a valid Verifiable-Work Envelope.

No evidence means no verified completion.

---

## 5.8 Agent Type Does Not Grant Authority

An Agent type describes its intended operating pattern.

Authority must come from:

- approved Role;
- approved Agent Definition;
- valid allocation;
- valid delegation;
- valid permissions;
- current approval;
- runtime enforcement.

---

## 5.9 Higher Hierarchy Does Not Mean Unlimited Access

An L1 or L2 Agent may have broader coordination responsibility.

It must still remain:

- permission-bound;
- Product-aware;
- Project-aware;
- Tenant-aware;
- environment-aware;
- auditable;
- revocable.

---

## 5.10 Runtime Claims Require Runtime Evidence

Documentation does not prove:

- registration;
- provisioning;
- allocation;
- activation;
- live testing;
- Production operation.

# 8. Role Versus Agent Type

## Role

A Role defines:

- organizational purpose;
- responsibilities;
- authority boundaries;
- required skills;
- expected outcomes;
- reporting line;
- escalation path.

## Agent Type

An Agent type defines:

- operating behavior;
- execution pattern;
- collaboration pattern;
- autonomy pattern;
- Risk characteristics;
- evidence expectations.

One Role may permit more than one Agent type.

One Agent type may support multiple approved Roles.

---

# 9. Agent Definition Versus Agent Instance

## Agent Definition

An Agent Definition is a governed specification containing:

- definition ID;
- Role;
- Agent type;
- purpose;
- capabilities;
- prompts;
- Models;
- Tools;
- authority;
- permissions;
- memory;
- evaluation;
- budget;
- evidence;
- lifecycle rules.

## Agent Instance

An Agent Instance is one registered runtime identity created from an approved
Agent Definition.

It must have:

- unique instance ID;
- accountable Human owner;
- exact definition version;
- runtime configuration;
- allocation;
- lifecycle state;
- monitoring;
- runtime evidence.

---

# 10. Agent Session Versus Runtime Worker

## Agent Session

An Agent Session is a time-bounded context for:

- one Agent Instance;
- one approved objective;
- one Product or Project scope;
- one Tenant or Customer scope;
- one environment;
- one authority context.

## Runtime Worker

A Runtime Worker is a technical execution unit that processes part or all of a
Task.

One Agent Instance may use multiple workers only when:

- concurrency is approved;
- scope isolation is enforced;
- cost limits are active;
- monitoring is active;
- evidence remains attributable.

| Dimension | Classification Question |
|---|---|
| Hierarchy | Where does the Agent operate in the reporting structure? |
| Functional Type | What kind of value does the Agent provide? |
| Execution Mode | Does it observe, advise, draft, coordinate, review, or execute? |
| Autonomy | How independently may it operate? |
| Risk | What is the maximum impact of its permitted actions? |
| Scope | Which Organization, Product, Project, Tenant, and Customer may it support? |

| Duration | Is it persistent, temporary, scheduled, or event-driven? |
| Collaboration | Does it work alone, in a Team, or as an orchestrator? |
| Data | Which Data classifications may it access? |
| Tooling | Which Tool-action categories may it use? |
| Lifecycle | What is its current governed state? |

No single classification dimension is sufficient.

# 12. Hierarchy-Based Agent Types

The target hierarchy is:

```text
L0 — Founder and Human Constitutional Authority
L1 — Executive Coordination Agent
L2 — C-Suite Domain Agent
L3 — Department Director Agent
L4 — Manager or Team Lead Agent
L5 — Specialist or Execution Agent
```

L0 is not an AI Agent type.

---

# 13. L1 Executive Coordination Agent

An L1 Agent supports enterprise-level coordination.

Typical example:

```text
AI Chief Executive Officer
```

Primary functions may include:

- strategy translation;
- executive coordination;
- portfolio visibility;
- enterprise prioritization;
- cross-department dependency management;
- Founder decision preparation;
- Risk escalation.

An L1 Agent must not:

- replace the Founder;
- amend Governance;
- activate itself;
- approve its own authority;
- sign contracts;
- transfer funds;
- accept Founder-reserved Risk;
- grant unrestricted Production access.

- retrieves approved context;
- analyzes evidence;
- identifies options;
- identifies uncertainty;
- identifies Risks;
- prepares recommendations;
- identifies required decisions.

It must not:

- represent recommendations as approved decisions;

- conceal uncertainty;
- fabricate evidence.

```text

Analyze
Recommend
Escalate
```

# 41. Agent Operating Modes

An Agent may operate in one or more approved modes.

| Code | Mode | Meaning |
|---|---|---|
| `MODE-OBSERVE` | Observe | Read approved signals and report |
| `MODE-ADVISE` | Advise | Analyze and recommend |
| `MODE-DRAFT` | Draft | Prepare non-final artifacts |
| `MODE-PLAN` | Plan | Prepare structured execution plans |
| `MODE-COORDINATE` | Coordinate | Manage approved dependencies and handoffs |
| `MODE-REVIEW` | Review | Assess work against criteria |
| `MODE-VERIFY` | Verify | Validate evidence and claims |
| `MODE-EXECUTE` | Execute | Perform approved actions |
| `MODE-RECOVER` | Recover | Perform approved rollback or recovery |
| `MODE-RESPOND` | Respond | Support approved incident or Customer response |

Operating mode must be enforced by permissions.

# 42. Autonomy Classification

| Code | Autonomy Level | Permitted Pattern |
|---|---|---|
| `AUT-0` | Observe Only | Retrieve and report approved information |
| `AUT-1` | Advisory | Analyze, compare, and recommend |
| `AUT-2` | Drafting and Planning | Create non-final drafts and plans |
| `AUT-3` | Controlled Internal Execution | Perform reversible low-to-medium-Risk internal work |
| `AUT-4` | Supervised Production Execution | Perform narrowly approved Production work with active oversight |
| `AUT-5` | Exceptional Emergency Execution | Perform pre-authorized emergency action under strict control |

`AUT-5` must not represent general autonomy.

It requires:

- exact emergency conditions;
- pre-approved actions;
- narrow targets;
- strong audit;
- monitoring;
- Human incident authority;
- post-action review;
- immediate revocation capability.

---

# 43. Autonomy Does Not Equal Risk

Autonomy and Risk are separate.

Example:

```text
A highly autonomous monitoring Agent may remain R1.

A low-autonomy legal or financial recommendation may still be R3.
```

Every Agent must have both:

- autonomy classification;
- Risk ceiling.

---

# 44. Risk Classification

| Risk | Agent Work Interpretation |
|---|---|
| `R0` | Read-only, public, or negligible-impact work |
| `R1` | Reversible internal analysis, drafting, or documentation |
| `R2` | Controlled internal execution with bounded impact |
| `R3` | Production, Customer, Security, privacy, financial, or material operational impact |
| `R4` | Irreversible, destructive, constitutional, legal, regulated, or enterprise-critical impact |

R3 and R4 work requires qualified Human review and approval.
