# Mianx.ai AI Workforce Skill Registry

> **This document defines the governed target-state Registry for all Skill
> Definitions, Skill Profiles, Role Skill Requirements, Agent Skill
> Assignments, proficiency decisions, evaluations, certifications,
> restrictions, renewals, revocations, and runtime Skill eligibility across the
> Mianx.ai Shared AI Workforce.**

- another Agent possesses a related Skill.

This document does not independently:

- approve a Skill Definition;
- grant a Skill to an Agent;
- approve proficiency;
- issue certification;
- assign a Role;
- approve a Capability;
- grant Tool access;
- approve a Model;
- activate an Agent;
- authorize Production Skill use;
- prove runtime Skill eligibility.

# 5. Core Skill Registry Principles

## 5.1 Skills Must Be Explicitly Defined

Every Skill must have:

- stable identity;
- exact version;
- clear definition;
- bounded purpose;
- expected outcomes;
- owner;
- category;
- Risk;
- evaluation;
- evidence;
- lifecycle.

---

## 5.2 Skill Claims Require Evidence

A Skill claim without valid evidence must be classified as:

```text
UNVERIFIED
```

---

## 5.3 Role Requirements Do Not Prove Agent Skill

A Role may require a Skill.

The requirement does not prove that a specific Agent possesses it.

---

## 5.4 Training Does Not Grant Proficiency

Training may prepare an Agent for evaluation.

Training completion does not independently grant:

- proficiency;
- certification;
- runtime eligibility;
- Production authority.

---

## 5.5 Tool Access Does Not Prove Skill

An Agent may have access to a Tool without possessing the Skill required to use
it safely or correctly.

---

## 5.6 Model Capability Does Not Prove Agent Skill

A Model may produce related output.

The complete Agent configuration must still be evaluated.

---

## 5.7 Skills Must Be Version-Specific

A proficiency or certification decision applies to:

- exact Skill version;
- exact Agent Definition version;
- exact Agent Instance where applicable;
- exact runtime version;
- relevant prompt version;
- relevant Tool Profile;
- relevant Model Profile;
- relevant environment.

---

## 5.8 Skills Must Be Scope-Bound

Skill validity may depend on:

- Product;
- Project;
- Tenant;
- Customer;
- environment;
- region;
- Data class;
- Tool;
- Model;
- workflow;
- Risk.

---

## 5.9 High-Risk Skills Require Stronger Assurance

High-risk Skills require stronger:

- evaluation;
- certification;
- Human review;
- monitoring;
- expiry;
- restriction;
- suspension;
- revocation.

---

## 5.10 Skills Must Be Revocable

Every active Skill Assignment must support:

- restriction;
- suspension;
- expiry;
- revocation;
- replacement;
- retirement.

---

## 5.11 Registry Status Must Match Runtime Truth

A Registry record must not report a Skill as active when:

- evaluation expired;
- certification expired;
- Agent lifecycle is invalid;
- allocation expired;
- dependencies are unavailable;
- suspension exists.

---

## 5.12 Skill Claims Must Remain Current-State Accurate

Documentation must distinguish:

```text
DEFINED

APPROVED

ASSIGNED

EVALUATED

CERTIFIED

ACTIVE

PRODUCTION-AUTHORIZED
```

These states must not be collapsed.

# 7. Skill Definition

A Skill Definition describes a governed, testable, and evidence-supported
ability to perform a bounded type of work.

It should define:

- expected behavior;
- expected outcome;
- required inputs;
- permitted methods;
- prohibited behavior;
- required dependencies;
- proficiency model;
- evaluation;
- evidence;
- Risk;
- validity;
- lifecycle.

---

# 8. Skill Profile

A Skill Profile defines the approved configuration and conditions under which
a Skill may be evaluated or used.

A Skill Profile may include:

- required Agent types;
- required Roles;
- required capabilities;
- required Tools;
- required Models;
- required prompts;
- required memory;
- required workflows;
- Data scope;
- environment;
- Risk;
- evaluation profile;
- certification profile;
- evidence profile;
- monitoring profile.

---

# 9. Role Skill Requirement

A Role Skill Requirement defines:

- which Skill a Role requires;
- minimum proficiency;
- whether the Skill is mandatory;
- whether certification is required;
- permitted scope;
- review cycle;
- restrictions.

A Role Skill Requirement does not assign the Skill to an Agent.

---

# 10. Agent Skill Assignment

An Agent Skill Assignment connects:

- one Skill Definition;
- one Agent Definition or Agent Instance;
- one Role;
- one required or approved proficiency;
- one scope;
- one lifecycle state;
- one evidence chain.

An assignment does not prove proficiency until evaluation is completed.

---

# 11. Proficiency Decision

A Proficiency Decision records the approved Skill level demonstrated by an
exact Agent configuration.

It must identify:

- Skill;
- Agent;
- evaluated level;
- approved level;
- scope;
- environment;
- evaluator;
- evidence;
- validity;
- restrictions.

---

# 12. Skill Certification

Skill Certification is a time-bounded assurance record confirming that an
exact Agent configuration passed an approved evaluation for an exact Skill,
level, scope, and Risk.

Certification does not grant broader authority than the underlying Role,
allocation, or permission.

---

# 13. Skill Registry Entry

A Skill Registry Entry is the governed source-of-truth record for one Skill
Definition and its lifecycle.

It should contain:

- Skill ID;
- version;
- name;
- category;
- family;
- owner;
- definition;
- proficiency model;
- dependencies;
- Risk;
- evaluation;
- certification requirement;
- scope;
- lifecycle state;
- approval state;
- review date;
- evidence.

# 24. Skill Families

A Skill Family groups related Skill Definitions.

Example:

```text
Engineering Skill Family
├── Requirements Analysis
├── Architecture Analysis
├── Backend Engineering
├── Frontend Engineering
├── Database Engineering
├── Automated Testing
├── Repository Change Management
├── Release Preparation
└── Deployment Verification
```

Membership in a Skill Family does not grant every child Skill.

# 27. Skill Proficiency Levels

The proposed proficiency scale is:

| Code | Level | Meaning |
|---|---|---|
| `SP-0` | Not Evaluated | No valid proficiency evidence exists |
| `SP-1` | Awareness | Understands terminology and basic boundaries |
| `SP-2` | Assisted | Performs bounded work with detailed guidance |
| `SP-3` | Independent | Performs routine approved work independently |
| `SP-4` | Advanced | Handles complex work and supports review |
| `SP-5` | Expert | Handles exceptional complexity and designs standards |
| `SP-6` | Assessor | Authorized to evaluate the Skill of others within approved scope |

---

# 28. Proficiency Rules

- `SP-0` must not be treated as Skill possession.
- `SP-1` does not authorize independent execution.
- `SP-2` requires active supervision.
- `SP-3` may support routine bounded work.
- `SP-4` may support complex work and review.
- `SP-5` may support advanced design and standard development.
- `SP-6` requires explicit assessor authorization.

Higher proficiency does not automatically grant:

- broader authority;
- broader permissions;
- broader Product scope;
- broader Project scope;
- broader Tenant scope;
- Production access;
- higher financial limits.

# 93. Skill Suspension

A Skill should be suspended when:

- evaluation becomes invalid;
- certification expires;
- Skill is used outside scope;
- Tool is compromised;
- Model behavior changes materially;
- memory contamination affects the Skill;
- evidence is fabricated;
- repeated failure occurs;
- Product isolation fails;
- Project isolation fails;
- Tenant isolation fails;
- critical policy violation occurs;
- valid Governance instruction exists.

Suspending one Skill does not automatically retire the entire Agent.

# 94. Skill Suspension Procedure

Skill suspension must:

1. identify the Skill Assignment;
2. identify affected capabilities;
3. block new Tasks requiring the Skill;
4. stop or contain active high-risk work;
5. restrict dependent Tools;
6. restrict dependent Models;
7. restrict dependent memory;
8. preserve evidence;
9. identify affected Products and Projects;
10. identify affected Tenants and Customers;
11. notify accountable owners;
12. create incident or review record;
13. define remediation;
14. define reactivation conditions;
15. verify suspension effectiveness.
