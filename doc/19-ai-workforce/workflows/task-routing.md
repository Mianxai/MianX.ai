# Mianx.ai Enterprise Human and AI Workforce Task Routing Standard

> **This document defines the governed target-state standard for routing
> Tasks across Mianx.ai. It governs Task sources, destinations, Route IDs,
> route versions, routing policies, policy precedence, Department, Team,
> Human, Agent Pool, Shared Service, Product, Project, Customer, Tenant,
> Customer Edition, Role, Skill, Capability, Tool, Model, memory, queue,
> priority, deadline, Risk, capacity, workload, context, deterministic and
> policy-based routing, fallback routes, rerouting, loop prevention,
> dead-letter handling, acknowledgement, evidence, observability, audit,
> and Production Task Routing gates.**

---

# 1. Purpose

The purpose of Task Routing is to determine:

```text
WHERE
AND
THROUGH WHICH GOVERNED PATH
A VALID TASK SHOULD MOVE
```

within the Mianx.ai operating architecture.

Task Routing must ensure that movement of work preserves:

- Task identity;
- Workflow context;
- Department boundaries;
- Team boundaries;
- Customer boundaries;
- Tenant boundaries;
- Product scope;
- Project scope;
- required Role;
- required capability;
- Risk;
- priority;
- capacity;
- authority;
- evidence.

Task Routing must not itself determine all final responsibility.

Final assignee selection is governed separately by:

```text
doc/19-ai-workforce/workflows/task-assignment.md
```

# 4. Foundational Routing Principle

```text
Valid Task
+
Valid Source
+
Approved Routing Policy
+
Valid Scope
+
Eligible Destination
+
Required Role / Capability Context
+
Capacity / Risk Constraints
+
Customer / Tenant Isolation
+
Traceable Route
=
Eligible Task Route
```

An eligible Task Route does not automatically create:

- a final assignee;
- execution authority;
- Task acceptance;
- Task completion.

---

# 5. Core Routing Rule

The routing system must answer:

```text
WHERE MAY THIS TASK LEGITIMATELY GO NEXT?
```

before attempting to optimize:

```text
WHERE WOULD IT BE FASTEST
CHEAPEST
OR MOST CONVENIENT TO SEND IT?
```

# 8. Task Routing Authority

Routing authority determines which approved actors or systems may move a Task
between governed destinations.

Possible routing authorities may include:

- Workflow Engine;
- Routing Engine;
- Task Governance;
- approved orchestration logic;
- Team Lead;
- Department authority;
- Shared Service control;
- authorized Human operator.

Routing authority must be bounded by policy.

---

# 9. Founder Sovereignty

Task Routing must not move Founder-reserved decisions or authority into
lower-level destinations without explicit Governance.

Routing does not alter enterprise authority hierarchy.

---

# 10. Qualified Human Accountability

Human review may be required for routing involving:

- critical Risk;
- privileged Security operations;
- sensitive Privacy context;
- legal or Compliance matters;
- financial commitments;
- Customer contractual commitments;
- ambiguous Customer/Tenant scope;
- high-autonomy Agent execution.

# 11. Task Routing Engine Boundary

The Task Routing Engine determines:

```text
SOURCE
→
GOVERNED PATH
→
DESTINATION
```

The Task Assignment Engine separately determines:

```text
ELIGIBLE RESPONSIBLE ASSIGNEE
```

The Workflow Engine separately governs:

```text
WORKFLOW STATE AND EXECUTION CONTEXT
```

---

# 12. Routing vs Assignment

```text
ROUTING:
Where should the Task move?

ASSIGNMENT:
Who should become responsible for the Task?
```

Example:

```text
Task
↓
Engineering Department Queue
↓
Backend Team Queue
↓
Eligible Agent Pool
```

is routing.

Selecting:

```text
AGENT-ENG-BACKEND-017
```

as the primary assignee is assignment.

# 127. Anti-Gaming Controls

Routing Governance must prevent:

- sending Tasks to cheaper destinations that fail hard controls;
- routing to fast but unauthorized Teams;
- routing to overloaded destinations to inflate utilization;
- hiding reroutes;
- hiding dead-letter volume;
- resetting hop count to evade loop controls;
- changing Routing Policy after seeing preferred outcome;
- ignoring failed Customer isolation attempts;
- ignoring failed Tenant isolation attempts;
- treating route acknowledgement as Task acceptance;
- routing directly to a preferred Agent to bypass Assignment Governance;
- using fallback routes as permanent unapproved routes;
- routing Tasks between Departments to avoid accountability;
- counting routed Tasks as completed Tasks.
