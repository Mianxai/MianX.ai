# Mianx.ai AI Workforce Security Policy

> **This policy defines the governed target-state Security requirements for
> Human workers, AI Agents, Teams, Departments, Products, Projects, Customer
> Editions, Customers, Tenants, identities, Roles, responsibilities,
> credentials, sessions, Tools, Models, memory, Data, providers, infrastructure,
> workflows, Tasks, and Production environments operating within the Mianx.ai
> enterprise ecosystem.**

---

# 1. Purpose

This policy establishes the official AI Workforce Security requirements for
Mianx.ai.

It defines:

- Security authority;
- Founder Security authority;
- qualified Human accountability;
- Security ownership;
- Security principles;
- Human Security responsibilities;
- AI Agent Security responsibilities;
- Team and Department Security;
- Product and Project Security;
- Customer and Tenant Security;
- identity Security;
- authentication;
- authorization;
- least privilege;
- separation of duties;
- privileged access;
- credentials;
- secrets;
- sessions;
- Tool Security;
- Model Security;
- memory Security;
- Data Security;
- environment Security;
- endpoint Security;
- network Security;
- infrastructure Security;
- application and API Security;
- provider Security;
- supply-chain Security;
- change Security;
- vulnerability management;
- patching;
- secure development;
- logging;
- monitoring;
- detection;
- Incident Response;
- access review;
- suspension;
- revocation;
- retention;
- evidence;
- audit;
- exceptions;
- violations;
- Production Security gates;
- current-state boundaries.

This policy ensures that a subject is not considered secure merely because:

- a password exists;
- multi-factor authentication is available;
- an account is disabled;
- a Role is documented;
- an Agent Definition exists;
- a Tool is approved;
- a Model is popular;
- encryption is mentioned;
- logs are generated;
- a Security review occurred;
- a vulnerability ticket exists;
- an Incident was contained;
- documentation is marked complete.

This policy does not independently:

- activate Security controls;
- create a Security Role;
- authorize Production access;
- approve an AI Agent;
- grant Tool access;
- grant Model access;
- grant memory access;
- grant Data access;
- prove Customer or Tenant isolation;
- prove vulnerability remediation;
- prove Incident readiness;
- prove Production Security enforcement.

# 3. Strategic Alignment

Security must preserve the exact Mianx.ai hierarchy:

```text
Mianx.ai Company and Governance
↓
MianX Core Platform
↓
Mianx.ai AI Operating System
↓
Shared AI Workforce
↓
Industry Operating Systems
↓
Customer Editions
↓
Autonomous Enterprise Creation at Scale
```

Security controls must not allow:

- a Customer Edition to override Company Governance;
- an Industry Operating System to override Core Platform Security;
- a Project to redefine Product Security ownership;
- a Customer to own Mianx.ai workforce identities;
- one Tenant to access another Tenant;
- an AI Agent to claim Founder or Human Security authority;
- operational urgency to permanently bypass Security controls;
- a temporary exception to become permanent unrestricted access.

12. defense in depth;
13. minimum necessary Data;

19. transparent limitations;

DENY

- Role approval;
- responsibility assignment;
- need validation;
- scope validation;
- Security review;
- authorization;
- expiry definition;
- monitoring activation;
- revocation readiness.

- approve identity assurance requirements;
- approve authentication methods;
- approve access;
- approve privileged access;
- approve Security configurations;
- approve Tool Security;
- approve Model Security;
- approve memory and Data Security;
- approve Customer and Tenant access;
- approve Production access;
- suspend access;
- revoke access;
- accept residual Security Risk;
- authorize Security exceptions;
- declare Security Incidents;

Security authority must be:

- explicit;
- current;
- Role-based;
- scope-bounded;
- environment-specific;
- Product-specific;
- Project-specific;
- Customer-specific;
- Tenant-specific;
- Risk-bounded;

# 11. Founder Security Authority

Founder authority is preserved for:

- Company-wide Security direction;
- AI Constitution Security principles;
- enterprise Risk tolerance;
- major executive Security authority;
- existential Security Risk;
- unrestricted AI autonomy;
- major Production Security exceptions;
- enterprise-wide shutdown or restoration;
- Company dissolution or ownership matters;
- matters explicitly reserved to the Founder.

Founder notification must not be represented as Founder approval.

# 18. Human Workforce Security Responsibilities

Human workers must:

- protect credentials;
- use approved authentication methods;
- use approved devices and environments;
- follow least privilege;
- avoid credential sharing;
- preserve Customer and Tenant confidentiality;
- use approved Tools and Models;
- report suspicious activity;
- preserve evidence;
- follow Security Incident instructions;
- complete required training;
- accept periodic access review;
- return assets and revoke access during offboarding.

---

# 19. Human Security Prohibitions

Humans must not:

- share passwords or secrets;
- approve their own critical access where separation is required;
- bypass monitoring;
- disable Security controls without authority;
- export restricted Data without approval;
- cross Customer or Tenant boundaries;
- use unapproved external services for restricted work;
- retain credentials after offboarding;
- suppress Security Incidents;
- fabricate Security evidence.

---

# 20. AI Agent Security Responsibilities

AI Agents must:

- operate under verified Agent identity;
- use an approved Agent Role;
- remain within assigned scope;
- use only approved Tools;
- use only approved Models;
- use only approved memory scopes;
- use only approved Data scopes;
- follow Product and Project boundaries;
- follow Customer and Tenant boundaries;
- disclose uncertainty;
- reject prohibited actions;
- preserve execution evidence;
- escalate Security concerns;
- stop when suspended or revoked.

---

# 21. AI Agent Security Boundary

An AI Agent must not:

- create its own authority;
- create unrestricted credentials;
- change its own Security Role;
- expand its own Tool permissions;
- expand its own memory access;
- expand its own Data access;
- approve its own critical output;
- accept material residual Risk;
- authorize Production restoration;
- notify external authorities;
- delete Incident evidence;
- reactivate itself after suspension;
- fabricate Human or Founder approval.
