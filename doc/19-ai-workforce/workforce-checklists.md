# Mianx.ai AI Workforce Checklists

> **The Mianx.ai AI Workforce Checklists provide governed, evidence-based,
> repeatable verification controls for documenting, reviewing, approving,
> registering, provisioning, evaluating, allocating, activating, monitoring,
> suspending, reactivating, retiring, and auditing AI Workforce entities without
> confusing planned state, documented state, approved state, implemented state,
> runtime state, or Production readiness.**

# 3. Checklist Objective

The primary objective is to prevent unsupported completion and readiness
claims.

```text
Requirement Defined
      ↓
Checklist Selected
      ↓
Control Item Evaluated
      ↓
Evidence Attached
      ↓
Reviewer Identified
      ↓
Failure or Gap Recorded
      ↓
Required Remediation Completed
      ↓
Independent Verification Where Required
      ↓
Approval Recorded
      ↓
State Updated
```

Every material checklist should answer:

- Which entity is being checked?
- Which exact version is being checked?
- Which scope is being checked?
- Who completed the checklist?
- Who reviewed it?
- Which evidence supports each completed item?
- Which items failed?
- Which items are not applicable?
- Who approved each exception?
- Which blockers remain?
- Which next state is being requested?
- Which authority can approve that transition?

# 4. Checklist Principles

## 4.1 Evidence Before Check Marks

A checked box without evidence must not be treated as verified completion.

---

## 4.2 One Checklist Per Exact Scope

A checklist must identify the exact:

- document;
- Role;
- Agent;
- capability;
- Product;
- Project;
- Tenant;
- environment;
- version;
- transition.

---

## 4.3 Not Applicable Requires Reason

`N/A` must include:

- reason;
- approving reviewer where material;
- affected scope;
- Risk assessment where appropriate.

---

## 4.4 Failed Items Must Remain Visible

A failed item must not be removed, hidden, or rewritten to make a checklist
appear complete.

---

## 4.5 Documentation Is Not Implementation

A documentation checklist may prove document completeness.

It does not prove runtime implementation.

---

## 4.6 Implementation Is Not Production Readiness

Implemented functionality must still pass:

- evaluation;
- Security review;
- operational review;
- monitoring review;
- incident-readiness review;
- Production approval.

---

## 4.7 High-Risk Checklists Require Human Review

R3 and R4 transitions require authorized Human review.

---

## 4.8 Checklist Completion Does Not Grant Authority

Authority must come from approved Governance and runtime permissions.

---

## 4.9 Checklists Must Be Versioned

A checklist must identify the version of the framework used.

---

## 4.10 Checklist Results Must Be Auditable

Material checklist results must preserve:

- executor;
- reviewer;
- date;
- evidence;
- outcome;
- limitations;
- approval;
- expiry or review date.

# 6. Checklist Item Status

Each checklist item should use one of:

```text
[ ] Not Verified

[x] Verified

[-] Not Applicable

[!] Failed

[~] Partially Verified

[?] Evidence Required
```

Recommended interpretation:

| Marker | Meaning |
|---|---|
| `[ ]` | Not yet evaluated or not verified |
| `[x]` | Requirement verified with acceptable evidence |
| `[-]` | Not applicable with documented reason |
| `[!]` | Requirement failed |
| `[~]` | Partially complete or conditionally satisfied |
| `[?]` | Claimed complete but supporting evidence is missing |

```text

E1 — Unverified Statement

E2 — Reviewed Document
```

# 11. Checklist Result Rules

A checklist may pass only when:

- all mandatory items are verified;
- all evidence requirements are satisfied;
- failed items are resolved;
- partial items are accepted through authorized conditions;
- exceptions are approved and unexpired;
- required reviewers completed review;
- required approvers recorded explicit decisions;
- requested lifecycle transition is valid.

A checklist must fail when:

- a critical mandatory control fails;
- required authority is missing;
- required evidence is fabricated or unavailable;
- Security or Tenant isolation is unverified for Production scope;
- suspension is unavailable for an operational Agent;
- Product, Project, or Tenant scope is ambiguous;
- runtime state conflicts with reported state.

---

# 12. Critical Control Marker

Items marked `CRITICAL` must block the requested transition when failed.

Examples include:

- missing accountable owner;
- missing identity;
- missing authority;
- missing Product or Project scope;
- missing Tenant isolation;
- missing Production approval;
- missing Security review;
- unapproved Tool or Model;
- missing audit;
- missing suspension;
- unresolved critical incident.
