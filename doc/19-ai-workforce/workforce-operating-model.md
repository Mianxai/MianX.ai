# Mianx.ai AI Workforce Operating Model

> **The Mianx.ai AI Workforce Operating Model defines how approved enterprise
> demand enters the Workforce, becomes governed work, receives an accountable
> owner and authorized Agent, is executed within Product, Project, Tenant,
> Security, cost, and quality boundaries, produces verifiable evidence, receives
> Human review, and closes with measurable outcomes and controlled Knowledge
> capture.**

---

# 1. Document Purpose

This document defines the day-to-day operating model of the Mianx.ai AI
Workforce.

It translates the AI Workforce Vision and Strategy into a governed operating
system for:

- receiving enterprise demand;
- defining objectives;
- creating work requests;
- classifying work;
- identifying Product, Project, Tenant, and environment;
- assessing Risk;
- selecting approved capabilities;
- selecting authorized Agents;
- checking capacity;
- assigning work;
- verifying authority;
- executing tasks;
- using approved models and tools;
- controlling cost;
- collecting evidence;
- conducting Human or authorized review;
- accepting, rejecting, or returning work;
- escalating uncertainty or Risk;
- handling failures and incidents;
- closing tasks;
- capturing verified learning;
- reviewing Workforce performance;
- improving operating processes.

This document defines the target operating model.

It does not independently:

- activate AI Agents;
- create runtime identities;
- grant permissions;
- authorize Tool use;
- authorize Model use;
- authorize provider spending;
- authorize Production access;
- prove Multi-Project operation;
- prove Tenant isolation;
- prove active AI departments;
- prove Production Operational status.

# 3. Operating Model Objective

The primary objective is to ensure that every material AI Workforce activity
follows a controlled path:

```text
Approved Demand
      ↓
Defined Objective
      ↓
Governed Work Request
      ↓
Risk and Scope Classification
      ↓
Capability and Agent Selection
      ↓
Authority and Capacity Verification
      ↓
Controlled Execution
      ↓
Evidence Production
      ↓
Quality and Human Review
      ↓
Acceptance, Rework, Rejection, or Escalation
      ↓
Task Closure
      ↓
Cost Attribution
      ↓
Verified Knowledge Capture
      ↓
Performance and Process Improvement
```

No material work should bypass this lifecycle.

# 5. Operating Principles

## 5.1 No Work Without Identity

Every material activity must have:

- a work-request ID;
- a task ID;
- an accountable owner;
- an assigned Product;
- an assigned Project;
- a Tenant where applicable;
- an assigned Agent or Human executor.

---

## 5.2 No Agent Without Authority

An Agent must not execute material work unless its:

- identity;
- Role;
- permissions;
- Product scope;
- Project scope;
- Tenant scope;
- Tool access;
- Model access;
- budget;
- runtime status;

are valid for the assigned work.

---

## 5.3 No High-Risk Action Without Human Approval

High-risk actions require Human approval before execution.

Examples include:

- Production deployment;
- destructive change;
- permission expansion;
- Customer Data export;
- Security exception;
- legal commitment;
- financial transfer;
- material pricing decision;
- sensitive communication;
- irreversible action.

---

## 5.4 No Completion Without Evidence

Material work must not be marked complete without evidence matching the exact
acceptance criteria.

---

## 5.5 No Shared Workforce Without Isolation

Shared Workforce capability must preserve:

- Tenant isolation;
- Project isolation;
- Product boundaries;
- Customer confidentiality;
- memory boundaries;
- secret boundaries;
- cost attribution.

---

## 5.6 No Learning Without Validation

Agent output must not automatically become organizational Knowledge.

Learning must be:

- evidenced;
- reviewed;
- classified;
- approved;
- versioned.

---

## 5.7 No Scale Without Operations

Workforce scale must not exceed:

- monitoring;
- audit;
- Human review capacity;
- Security capacity;
- support capacity;
- cost capacity;
- incident-response capacity;
- recovery capacity.

# 6. Operating Model Layers

The AI Workforce Operating Model contains nine operating layers.

```text
Layer 1 — Governance and Authority

Layer 2 — Demand and Portfolio Management

Layer 3 — Product, Project, Tenant, and Environment Context

Layer 4 — Workforce Organization and Capacity

Layer 5 — Capability, Agent, Tool, and Model Selection

Layer 6 — Task Execution and Orchestration

Layer 7 — Evidence, Quality, and Approval

Layer 8 — Operations, Incidents, Cost, and Performance

Layer 9 — Knowledge, Learning, and Improvement
```

Each layer has separate ownership and controls.

# 20. Demand Triage

Demand triage determines whether a request should:

- proceed to Discovery;
- enter planning;
- become an immediate incident;
- be rejected;
- be deferred;
- be merged with existing work;
- be escalated;
- remain in Research.

Triage should evaluate:

1. Is the problem clear?
2. Is the requester authorized?
3. Is an accountable owner assigned?
4. Is the Product known?
5. Is the Project known?
6. Is the Tenant known where applicable?
7. Is the expected outcome measurable?
8. Is an existing capability sufficient?
9. Is the requested work legal and ethical?
10. Is the Risk acceptable?
11. Is required Data available?
12. Is budget available?
13. Is Human approval required?
14. Is the request urgent?
15. Is the request duplicated elsewhere?

# 24. Scope Definition

Every Work Request must define:

The work the Workforce is allowed to perform.

The work the Workforce must not perform.

- test;
- staging;
- Production read-only;
- Production write.

The Data the Workforce may access.

## Authority Scope

The actions the assigned Agent may perform.

# 25. Risk Classification

Every material Work Request should receive a Risk class.

| Risk | Description | Example Control |
|---|---|---|
| `R0` | Read-only, informational, no material impact | Logging and owner |
| `R1` | Reversible internal drafting or analysis | Review before use |
| `R2` | Controlled internal change | Tests, evidence, rollback |
| `R3` | Customer, Production, Security, financial, or personal-Data impact | Explicit Human approval |
| `R4` | Irreversible, legal, constitutional, regulatory, or enterprise-wide impact | Founder or highest designated authority |

Risk classification must consider:

- reversibility;
- Data sensitivity;
- Customer impact;
- financial impact;
- legal impact;
- Security impact;
- Production impact;
- scale;
- external communication;
- autonomy;
- operational dependency.

---

# 26. Priority Classification

Priority should be based on impact and urgency.

| Priority | Meaning |
|---|---|
| `P0 — Critical` | Active incident, severe Security, legal, financial, or Production threat |
| `P1 — High` | Material business, Product, Customer, or operational requirement |
| `P2 — Medium` | Important planned work with manageable delay |
| `P3 — Normal` | Standard backlog or improvement work |
| `P4 — Research` | Unvalidated idea or experiment |

Priority must not be assigned only by the requester without triage.

# 40. Tool Use

Before using a Tool, verify:

- Tool is approved;
- Tool version is approved;
- Agent Role is eligible;
- Product scope is permitted;
- Project scope is permitted;
- Tenant scope is permitted;
- environment scope is permitted;
- requested action is permitted;
- rate limits are available;
- cost is acceptable;
- logging is active.

Write-capable tools require stronger controls than read-only tools.

---

# 41. Model Use

Before using a Model, verify:

- provider is approved;
- model is approved;
- task type is permitted;
- Data use is permitted;
- region is permitted;
- context limits are understood;
- cost is within budget;
- quality is sufficient;
- fallback behavior exists where required.

High-risk output may require:

- Human review;
- second-model verification;
- deterministic validation;
- restricted context;
- stronger evidence.

---

# 42. Delegation

An Agent may delegate only when:

- delegation is permitted;
- receiving Agent is eligible;
- scope is explicit;
- authority is not expanded;
- Product, Project, and Tenant remain correct;
- evidence requirements are preserved;
- expiry is defined;
- delegation is recorded.

An Agent must not delegate authority it does not possess.
