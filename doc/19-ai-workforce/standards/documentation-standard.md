# Mianx.ai Enterprise AI Workforce Documentation Standard

> **This document defines the target-state standard for creating, identifying,
> structuring, classifying, reviewing, approving, versioning, validating,
> superseding, retaining, archiving, auditing, and using documentation across
> the Mianx.ai AI Workforce domain without confusing written documentation
> with approval, implementation, runtime verification, canonical authority,
> or Production operation.**

---

# 6. Documentation Truth Model

Mianx.ai documentation must distinguish at least these dimensions:

```text
CONTENT STATE

GOVERNANCE STATE

IMPLEMENTATION STATE

RUNTIME VERIFICATION STATE

PRODUCTION STATE
```

These dimensions must not be collapsed into one label.

---

# 7. Content State

Recommended content states are:

```text
EMPTY_PLACEHOLDER

OUTLINE

PARTIAL

CONTENT_COMPLETE_FOR_REVIEW

REVISION_REQUIRED

CONTENT_STABLE
```

`CONTENT_COMPLETE_FOR_REVIEW` means:

- the intended document scope has been written;
- required sections are present;
- the document can enter formal review.

It does not mean:

- approved;
- active;
- canonical;
- implemented;
- runtime verified;
- Production operational.

---

# 8. Governance State

Recommended Governance states are:

```text
DRAFT

IN_REVIEW

CHANGES_REQUESTED

APPROVAL_PENDING

APPROVED

ACTIVE

DEPRECATED

SUPERSEDED

RETIRED

ARCHIVED
```

A document must not skip required Governance gates without explicit authority.

---

# 9. Implementation State

Recommended implementation states include:

```text
NOT_APPLICABLE

NOT_IMPLEMENTED

PARTIALLY_IMPLEMENTED

IMPLEMENTED_UNVERIFIED

IMPLEMENTED_VERIFIED

SUSPENDED

RETIRED
```

Implementation state must refer to the system or control described by the
document, not merely to the existence of the Markdown file.

# 11. Production State

# 12. Canonical State

Canonical state must be a separate explicit property:

```text
canonical: false
```

or:

```text
canonical: true
```

Canonical means the document is the authoritative governed reference for its
defined scope.

Canonical does not automatically mean:

- implemented;
- runtime verified;
- Production operational.

# 14. Founder Sovereignty

Founder sovereignty must be preserved in documentation covering:

- Company identity;
- Company vision;
- Company mission;
- AI Constitution;
- enterprise hierarchy;
- Founder-reserved authority;
- major Product direction;
- unrestricted AI autonomy;
- existential Company Risk;
- enterprise-wide policy;
- enterprise-wide Production authority;
- matters explicitly reserved to the Founder.

Documentation must never:

- fabricate Founder approval;
- infer Founder approval from silence;
- infer Founder approval from document age;
- infer Founder approval from repository placement;
- infer Founder approval from a Human reviewer;
- infer Founder approval from Agent confidence.

# 19. Document ID Rules

Document IDs must be:

- unique;
- stable;
- uppercase unless an established namespace defines otherwise;
- machine-readable;
- human-readable;
- free of spaces;
- free of ambiguous Unicode characters;
- recorded in metadata;
- traceable in Changelog entries.

Document IDs must not be reused for a different document.

# 22. Repository Path Standard

A document must live in the folder responsible for its primary domain.

Example:

```text
doc/19-ai-workforce/standards/documentation-standard.md
```

The repository path itself does not create authority.

---

# 23. Path Stability

Paths should remain stable unless:

- responsibility changes;
- domain classification changes;
- repository architecture changes;
- a Governance-approved restructuring occurs.

A path move must review:

- inbound references;
- dependencies;
- related-document links;
- INDEX entries;
- ROADMAP entries;
- Changelog;
- scripts;
- automation;
- external references.

---

# 24. Duplicate Document Rule

Before creating a new governed document, authors should determine whether:

- an equivalent document already exists;
- a parent document already owns the scope;
- a child document should own the scope;
- the change belongs in an existing document.

Duplicate authority documents are prohibited where they create ambiguity.

# 41. Version Standard

Governed documents should use semantic versioning:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
1.0.0
```

---

# 42. Major Version

Increase `MAJOR` when there is a material change to:

- authority;
- scope;
- operating model;
- policy meaning;
- architecture meaning;
- Governance structure;
- control framework;
- document identity relationship;
- backward compatibility.

Example:

```text
1.4.3
→
2.0.0
```

---

# 43. Minor Version

Increase `MINOR` when adding material but backward-compatible content.

Examples:

- new section;
- new workflow;
- new evidence requirement;
- new control;
- new validation rule;
- new approved example.

Example:

```text
1.2.0
→
1.3.0
```

---

# 44. Patch Version

Increase `PATCH` for non-material corrections.

Examples:

- typo;
- broken link;

# 47. Draft State

`Draft` means:

- content may change;
- approval is not complete;
- canonical authority is not established unless explicitly governed through
  another mechanism;
- implementation must not rely on the draft as mandatory authority unless an
  approved exception exists.

---

# 48. Content Complete for Review

A document may record:

```text
CONTENT_STATUS=CONTENT_COMPLETE_FOR_REVIEW
```

when:

- expected subject coverage is complete;
- current-state limitations are explicit;
- next-document relationships are known;
- quality review can begin.

It does not mean approved.

---

# 49. In Review

`In Review` means:

- formal review has started;
- reviewers have been identified;
- review evidence is being collected;
- content remains subject to change.

---

# 50. Approval Pending

`Approval Pending` means:

- required review is complete or sufficiently complete;
- the document awaits authorized approval.

---

# 51. Approved

`Approved` means:

- the exact version has received required authorized approval.

Approval must not be inferred.

---

# 52. Active

`Active` means:

- the document is currently in force within its defined Governance scope.

An Approved document may still be waiting for an activation date.

---

# 53. Canonical

`canonical: true` means:

- this document is the authoritative reference for its exact subject and
  scope.

There should not be multiple conflicting canonical documents for the same
scope.

---

# 54. Deprecated

`Deprecated` means:

- the document remains available;
- new usage should normally stop;
- replacement or migration guidance exists or is being prepared.

---

# 55. Superseded

`Superseded` means:

- a newer valid document or version has replaced this document for current
  use.

The superseded document should identify its successor.

---

# 56. Retired

`Retired` means:

- the governed function is no longer active;
- the document remains for required historical, audit, or legal purposes.

---

# 57. Archived

`Archived` means:

- the document has been removed from active operational use;
- it remains available according to retention rules.

Archived does not mean deleted.

# 59. Document Lifecycle Rules

A document must not move to:

- `CONTENT_COMPLETE_FOR_REVIEW` while materially incomplete;
- `IN_REVIEW` without a review target;
- `APPROVED` without approval evidence;
- `ACTIVE` without activation authority where required;
- `CANONICAL` without canonical promotion authority;
- `SUPERSEDED` without a known successor;
- `ARCHIVED` without retention review;
- `DELETED` without records and legal-hold review.

```text

#### H4 — Detailed Subsection
```

# 63. Heading Naming

- describe content;
- remain concise;
- use stable terminology;
- avoid vague labels such as `Misc`;
- avoid decorative punctuation;
- support navigation.

---

# 64. Paragraph Standard

Paragraphs should:

- express one coherent concept;
- use complete sentences where appropriate;
- avoid unnecessary repetition;
- distinguish requirements from examples;
- distinguish current state from target state.

---

# 65. Normative Language

Preferred normative terms:

```text
MUST
MUST NOT
REQUIRED
SHALL
SHALL NOT
SHOULD
SHOULD NOT
MAY
```

Where uppercase normative language is used, its intent should be clear.

---

# 66. Requirement Strength

Recommended interpretation:

| Term | Meaning |
|---|---|
| `MUST` / `REQUIRED` | Mandatory unless an approved exception exists |
| `MUST NOT` | Prohibited unless a higher valid authority explicitly permits it |
| `SHOULD` | Expected default; deviation requires a reason |
| `SHOULD NOT` | Avoid unless justified |
| `MAY` | Optional within applicable Governance boundaries |

---

# 67. Lists

Use bullet lists when order does not matter.

Use numbered lists when:

- sequence matters;
- priority matters;
- lifecycle order matters;
- procedural order matters.

---

# 68. Tables

Tables should be used when structured comparison improves clarity.

Tables should:

- have meaningful column names;
- avoid excessive width where possible;
- contain one concept per cell;
- preserve status terminology.

---

# 69. Checklist Standard

Use:

```text

- [x] Completed control
```

A checked box must represent a supported state.

A checklist must not be pre-checked merely because the item is desirable.

---

# 70. Code Block Standard

Code blocks should use plain Markdown fences.

```text
```text

```
```

or:

```text

```
```

or:

```text

```
```

Custom fence attributes must not be added unless the repository rendering
standard explicitly requires and validates them.

For example, avoid undocumented constructs such as:

```text

```
```

when plain Markdown is sufficient.

# 71. Code Block Truth Rule

Code blocks must distinguish:

- example;
- pseudocode;

- target-state schema;
- Production configuration.
