# Folder Responsibility Matrix — Folders 21–30

## 1. Document Purpose

This document defines the proposed architectural responsibilities, ownership boundaries, permitted content, prohibited content, dependencies, consumers, governance relationships, and cross-folder boundaries for top-level folders `21-memory-engine` through `30-enterprise-governance`.

This document is a governed draft.

It does not authorize:

- Folder deletion
- Folder renaming
- Folder movement
- Document movement
- Document merging
- Duplicate-file deletion
- Content replacement
- Authority reassignment
- Canonical promotion
- Repository freeze

All responsibility assignments SHALL remain provisional until the actual contents of the affected folders, related folders, ownership model, architectural boundaries, and dependencies have completed formal review.

## 3. Interpretation Rules

### Rule 001 — Draft Authority

The assignments in this document represent proposed target responsibilities.

They SHALL NOT be treated as canonical while this document contains:

```yaml
status: Draft
canonical: false
```

---

### Rule 002 — Existing Content Protection

Existing folder structures, subfolders, and documents SHALL remain protected during responsibility analysis.

A duplicate filename, placeholder filename, overlapping subject, or incorrect location SHALL NOT automatically authorize deletion or movement.

Every proposed structural correction SHALL first receive:

- Content inspection
- Duplicate-content comparison
- Canonical-source decision
- Folder-boundary analysis
- Dependency analysis
- Reference-impact analysis
- Migration plan
- Governance approval
- Post-migration verification

---

### Rule 003 — One Primary Responsibility

Every top-level folder SHALL own one primary architectural responsibility.

Supporting responsibilities MAY exist only when they directly support the primary responsibility.

A supporting responsibility SHALL NOT redefine a subject canonically owned by another folder.

---

### Rule 004 — Engine Separation

Each engine folder SHALL define and own its internal capability.

An engine MAY integrate with another engine but SHALL NOT absorb the other engine’s internal responsibilities.

Example:

```text
20-ai-operating-system
Coordinates memory access

21-memory-engine
Owns memory storage, retrieval, consolidation and lifecycle
```

---

### Rule 005 — Organization and Runtime Separation

The repository SHALL distinguish between:

```text
AI Workforce
Defines which organizational agents exist

Agent Framework
Defines how an individual agent is technically structured

Multi-Agent System
Defines how multiple agents interact at runtime

AI Operating System
Coordinates the complete AI runtime
```

These responsibilities SHALL remain independently governable.

---

### Rule 006 — Research and Canonical Separation

Research content SHALL remain experimental until promoted through governance.

```text
26-research-lab
Produces hypotheses, experiments, evidence and proposals

Approved canonical folders
Consume promoted and approved outcomes
```

Research outputs SHALL NOT automatically become enterprise standards, production architecture, or runtime requirements.

---

### Rule 007 — Platform and Governance Separation

Enterprise platforms implement capabilities.

Enterprise governance defines how those capabilities are controlled.

Example:

```text
29-observability-platform
Implements observability capabilities

30-enterprise-governance
Defines governance, audit and oversight requirements
```

---

### Rule 008 — References Before Duplication

Where one folder consumes knowledge owned by another folder, it SHALL reference the canonical source rather than duplicate the full content.
