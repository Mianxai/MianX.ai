# Folder Responsibility Matrix — Folders 11–20

## 1. Document Purpose

This document defines the proposed architectural responsibilities, ownership boundaries, permitted content, prohibited content, dependencies, consumers, and cross-folder relationships for top-level folders `11-operations` through `20-ai-operating-system`.

This document is a governed draft.

It does not authorize:

- Folder deletion
- Folder renaming
- Folder movement
- Document movement
- Document merging
- Content replacement
- Canonical promotion
- Repository freeze

All assignments SHALL remain provisional until actual folder contents, ownership, dependencies, and responsibility boundaries have been reviewed through the Repository Stabilization Program.

---

## 2. Scope

This module covers exactly the following folders:

```text
11-operations
12-business
13-api
14-quality
15-ui-ux
16-knowledge
17-templates
18-assets
19-ai-workforce
20-ai-operating-system
```

Each folder SHALL appear in exactly one Folder Responsibility Matrix module.

---

## 3. Interpretation Rules

### Rule 001 — Draft Authority

The assignments in this document represent proposed target responsibilities.

They SHALL NOT be treated as canonical while the document contains:

```yaml
status: Draft
canonical: false
```

---

### Rule 002 — Existing Content Protection

Existing files and folders SHALL remain protected during responsibility analysis.

A responsibility conflict SHALL NOT automatically result in deletion, movement, renaming, or merging.

Every structural recommendation SHALL first receive:

- Content review
- Canonical-source analysis
- Boundary analysis
- Dependency analysis
- Migration impact analysis
- Governance approval

---

### Rule 003 — One Primary Responsibility

Every top-level folder SHALL own one primary architectural responsibility.

Supporting responsibilities MAY exist only when they directly support the primary responsibility.

---

### Rule 004 — Reference Before Duplication

Where a related subject is canonically owned by another folder, the consuming folder SHALL reference that source rather than redefining it.

---

### Rule 005 — Foundational and Specialized Separation

Folders `11–20` include foundational domains that may be implemented by later specialized platform folders.

Examples:

```text
13-api
    defines API engineering standards and interface specifications

37-api-platform
    defines the reusable API platform and runtime services
```

```text
14-quality
    defines quality engineering and assurance practices

46-enterprise-quality
    defines enterprise-wide quality governance and quality platform capabilities
```

```text
17-templates
    provides general reusable documentation and working templates

50-enterprise-templates
    provides governed enterprise template systems and organization-wide template catalogs
```
