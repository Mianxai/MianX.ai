# Folder Responsibility Matrix — Folders 31–40

## 1. Document Purpose

This document defines the proposed architectural responsibilities, ownership boundaries, permitted content, prohibited content, dependencies, consumers, authority relationships, and cross-folder boundaries for top-level folders `31-enterprise-architecture` through `40-enterprise-operations`.

This document is a governed draft.

It does not authorize:

- Folder deletion
- Folder renaming
- Folder movement
- Document movement
- Document merging
- Duplicate-file deletion
- Content replacement
- Authority reassignment
- Canonical promotion
- Repository freeze
- Implementation changes

All assignments SHALL remain provisional until actual folder contents, dependencies, references, ownership models, architectural boundaries, and governance relationships have completed formal review.

---

This module covers exactly the following folders:

```text
31-enterprise-architecture
```

---

## 3. Interpretation Rules

### Rule 001 — Draft Authority

The assignments in this document represent proposed target responsibilities.

They SHALL NOT be treated as canonical while this document contains:

```yaml
status: Draft
canonical: false
```

---

### Rule 002 — Existing Content Protection

Existing folder structures, documents, templates, local governance files, architecture files, strategy files, and lifecycle files SHALL remain protected during responsibility analysis.

A duplicate filename, overlapping subject, incorrect location, placeholder, or conflicting description SHALL NOT automatically authorize deletion, movement, or replacement.

Every proposed correction SHALL first receive:

- Content inspection
- Duplicate-content comparison
- Canonical-source decision
- Folder-boundary analysis
- Dependency analysis
- Reference-impact analysis
- Migration plan
- Governance approval
- Post-migration verification

---

### Rule 003 — One Primary Responsibility

Every top-level folder SHALL own one primary architectural responsibility.

Supporting responsibilities MAY exist only when they directly support the folder’s primary purpose.

A supporting responsibility SHALL NOT redefine a subject canonically owned by another folder.

---

### Rule 004 — Architecture and Implementation Separation

Architecture defines structure, principles, relationships, target states, constraints, and decisions.

Implementation platforms define executable capabilities.

```text
31-enterprise-architecture
Defines enterprise architecture

32-platform-services
Implements reusable platform services

37-api-platform
Implements API platform capabilities

39-deployment
Implements deployment capabilities
```

Architecture documentation SHALL NOT absorb platform implementation ownership.

---

### Rule 005 — Platform and Product Separation

Reusable platforms SHALL remain separate from user-facing or commercial products.

```text
32-platform-services
Provides reusable platform capabilities

33-marketplace
Provides marketplace business and product capabilities

38-developer-portal
Provides the developer-facing product experience
```

---

### Rule 006 — Runtime and Distribution Separation

The technical runtime for an extension SHALL remain separate from the commercial or organizational channel through which that extension is distributed.

```text
34-plugin-framework
Owns plugin runtime and extension mechanics

33-marketplace
Owns plugin listing, discovery, publishing and distribution
```

---

### Rule 007 — Interface and Consumer Separation

APIs, SDKs, CLI tools, and developer documentation SHALL remain separate responsibilities.

```text
37-api-platform
Provides and manages APIs

35-sdk
Provides programmatic client libraries

36-cli
Provides command-line access

38-developer-portal
Provides developer documentation and onboarding
```

---

### Rule 008 — Deployment, DevOps and Operations Separation

```text
10-devops
Defines software-delivery practices and CI/CD governance

39-deployment
Defines and executes environment deployment mechanisms

11-operations
Defines service-management and operational practices

40-enterprise-operations
Coordinates enterprise-wide operational capabilities
```

These folders MAY integrate but SHALL NOT collapse into one responsibility.

---

### Rule 009 — Specialized Platform Authority

Where a general platform folder and a specialized platform folder both discuss a capability, the specialized platform SHALL own the domain-specific implementation.

Example:

```text
32-platform-services
May provide a shared authentication service

41-security-platform
Owns enterprise security-platform capabilities

09-security
Owns security requirements and policies
```

---

### Rule 010 — References Before Duplication

Where one folder consumes knowledge owned by another folder, it SHALL reference the canonical source rather than duplicate the complete content.
