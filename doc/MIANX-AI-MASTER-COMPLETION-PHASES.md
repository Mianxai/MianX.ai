# MianX.ai Master Completion Phases

> [!IMPORTANT]
> This document defines the approved order and boundaries of MianX.ai
> enterprise phases.
>
> It does not independently prove implementation, deployment, Production
> operation, Customer adoption, active AI capability, or Phase completion.
>
> Current implementation and operational truth is governed by:
>
> - [`CURRENT-STATE.md`](./CURRENT-STATE.md)

> No Phase starts automatically because the previous Phase appears nearly
> complete.
>
> Every Phase requires:
>
> - verified entry criteria;
> - approved scope;
> - named ownership;
> - evidence-based exit criteria;
> - Founder progression approval.

# 1. Purpose

This document establishes one controlled enterprise progression model for
MianX.ai.

Its purpose is to prevent:

- premature Phase progression;
- uncontrolled Core expansion;
- Documentation-driven implementation;
- unsupported AI claims;
- parallel construction of several incomplete Products;
- Customer-specific Platform forks;
- duplicate enterprise foundations;
- new modules without verified users or workflows;
- Marketplace and global expansion before Product proof;
- incorrect claims of completion;
- repeated changes to the strategic direction.

This document defines:

- the current Phase;
- future Phase order;
- entry gates;
- scope;
- exclusions;
- evidence;
- exit gates;
- Founder authority;
- locked work;
- completion terminology;
- re-baselining rules.

# 3. Completion Philosophy

## 3.1 Completion Is Evidence-Based

A Phase is complete only when:

- approved outcomes exist;
- implementation exists where required;
- required tests pass;
- Security requirements pass;
- Production verification passes;
- operational ownership exists;
- recovery requirements are addressed;
- Documentation is synchronized;
- Customer or enterprise outcomes are measured where required;
- remaining risks are accepted by proper authority;
- Founder approval is recorded;
- approved work is merged and verified.

## 3.2 Time Does Not Complete a Phase

A Phase does not complete because:

- a target date passed;
- a document was created;
- code was written;
- tests exist;
- CI is green;
- a deployment succeeded;
- most work appears finished;
- a percentage appears high;
- the next Phase is more interesting;
- an AI Agent recommends progression.

## 3.3 No Official Percentage Completion

MianX.ai will not assign an official Phase completion percentage unless an
approved weighted measurement model exists.

Security, Production verification, Customer evidence, recovery, Governance,
and Founder authority cannot be reduced to an informal percentage.

# 4. One Active Phase Rule

MianX.ai should have only one formally active enterprise execution Phase at a
time.

Controlled discovery may occur for a future Phase only when:

- it does not create Production dependency;
- it does not create Customer commitment;
- it does not change Platform Architecture;
- it does not authorize AI execution;
- it does not consume critical current-Phase capacity;
- it is explicitly labelled Research or Discovery;
- the Founder approves the limited activity.

Future-Phase Documentation does not mean the Phase has started.

# 8. Platform Capability Layers

## 8.1 MianX Platform Kernel

The Kernel should contain only stable, broadly universal technical foundations.

Potential Kernel capabilities include:

- Authentication;
- Users;
- Organizations;
- Tenants;
- Memberships;
- roles;
- permissions;
- policy enforcement;
- configuration;
- feature flags;
- audit;
- event conventions;
- API standards;
- usage hooks;
- Security foundations;
- observability hooks.

A capability becomes a verified Kernel capability only after implementation,
testing, operational ownership, and suitable Product use evidence.

## 8.2 Shared Platform Services

Shared Platform Services may be reusable without belonging inside the Kernel.

Potential services include:

- Workspaces;
- Projects;
- tasks;
- approvals;
- workflows;
- comments;
- files;
- notifications;
- search;
- reporting;
- dashboards;
- documents;
- integration services.

## 8.3 Shared Enterprise Services

Potential Shared Enterprise Services include:

- CRM foundations;
- billing foundations;
- Customer onboarding;
- Customer Success;
- Support;
- procurement foundations;
- inventory foundations;
- finance foundations;
- reusable business analytics.

## 8.4 Industry Operating Systems

Industry Operating Systems own domain-specific:

- terminology;
- entities;
- business rules;
- workflows;
- permissions;
- reports;
- integrations;
- AI behavior;
- Customer outcomes.

Examples include:

- RestaurantOS;
- PoultryOS;
- future formally approved Industry Products.

## 8.5 Customer Editions

Customer variation should be handled through:

- configuration;
- roles;
- permissions;
- branches or locations;
- workflows;
- rules;
- templates;
- feature flags;
- data mappings;
- approved integrations;
- approved extensions.

Customer-specific Platform forks require explicit Architecture and Product
approval.

---

# 9. Capability Promotion Rule

A capability may move from Product-specific scope to a shared layer only when:

- at least one real Product need is verified;
- reuse value is demonstrated;
- a second use case exists or is strongly evidenced;
- domain-specific behavior can remain outside the shared contract;
- ownership is assigned;
- interfaces are defined;
- Security is reviewed;
- Tenant isolation is preserved;
- tests exist;
- migration impact is understood;
- operational support exists;
- cost is understood;
- Architecture approval is recorded.

A capability should not be promoted to Core to make a roadmap look complete.

# 19. Product Completion Model

MianX.ai Products should not be described as absolutely `100% complete`.

Products progress through maturity states.

| Product state | Meaning |
|---|---|
| Discovery | Problem, user, and evidence are being investigated |
| Validated | The problem and intended outcome are supported by evidence |
| Designed | Requirements, workflows, Architecture, and acceptance criteria exist |
| Pilot Ready | Limited controlled Customer use is ready |
| Pilot | A controlled real-user implementation is operating |
| Production Ready | Required Security, Quality, Operations, and recovery gates pass |
| Production Operational | Real users operate with monitoring, support, and ownership |
| Repeatable | Onboarding and configuration work for additional Customers |
| Scalable | Product supports increasing Customers and usage sustainably |
| Mature | Product has stable economics, lifecycle, Operations, and continuous improvement |
| Retired | Product is safely removed through an approved lifecycle |

A Product may continue improving after entering Production.
