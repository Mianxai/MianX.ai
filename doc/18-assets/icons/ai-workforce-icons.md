# Purpose

This document defines the official icon standards for AI workforce roles, capabilities, functions, teams, and execution contexts across the Mianx.ai ecosystem.

AI workforce icons provide compact visual identification inside:

- AI Agent Directories
- Workforce Dashboards
- Task Assignment Interfaces
- Agent Routing Systems
- Workflow Builders
- Orchestration Interfaces
- Review Queues
- Governance Dashboards
- Monitoring Systems
- Reports
- Documentation
- Developer Tools
- Administrative Interfaces

These icons must remain separate from permanent agent avatars, department icons, status icons, and product logos.

---

# Objectives

- Establish one official AI workforce icon language.
- Standardize role and capability identification.
- Separate AI identity from runtime status.
- Prevent duplicate or conflicting agent symbols.
- Support scalable workforce growth.
- Improve agent discovery and routing.
- Support accessible workforce interfaces.
- Enable reusable design-system components.
- Standardize icon metadata and mappings.
- Support AI-assisted asset discovery.
- Preserve governance and auditability.

# Core Principle

An AI workforce icon represents a role, capability, team, or function.

It must not:

- Replace the Mianx.ai company logo.
- Replace an AI agent avatar.
- Replace an agent name.
- Replace an official department icon.
- Represent runtime status.
- Imply human identity.
- Suggest authority beyond the agent’s approved permissions.
- Create an independent sub-brand.
- Misrepresent whether an agent is active, approved, or trusted.

---

# AI Workforce Icon vs Agent Avatar

| AI Workforce Icon | Agent Avatar |
|-------------------|--------------|
| Represents role or capability | Represents a specific agent identity |
| Reusable across multiple agents | Unique to one approved agent identity |
| Used in filters, routing, and dashboards | Used in profiles and conversations |
| Part of the icon system | Part of workforce identity system |
| Usually monochrome | May use approved identity styling |
| Inherits interface color | Uses governed avatar treatment |
| Does not include runtime status | May appear beside separate status indicator |

Example:

```text
Backend Engineering Icon
=
Represents the backend engineering capability

Backend Agent Avatar
=
Represents one specific backend AI agent
```

---

# AI Workforce Icon vs Department Icon

Department icons represent organizational ownership.

AI workforce icons represent operational roles or capabilities.

Example:

```text
Engineering Department Icon
=
Represents the Engineering organization

Code Review Agent Icon
=
Represents the code-review capability
```

An agent may belong to a department while using a distinct role icon.

---

# AI Workforce Icon vs Status Icon

AI workforce icons represent permanent role meaning.

Status icons represent temporary state.

Incorrect:

```text
Agent role icon permanently changed to green to mean running
```

Correct:

```text
[Agent Role Icon] Code Review Agent [Running Status]
```

Identity, role, and runtime status must remain separate.

# Role Family

A role family groups related AI roles.

Example:

```text
Engineering Role Family

├── Backend Engineering
├── Frontend Engineering
├── Mobile Engineering
├── QA Engineering
├── Architecture
└── Code Review
```

A shared family icon may be used where individual role detail is unnecessary.

# Role Icon

A role icon represents a stable operational responsibility.

Examples:

- Backend Engineer
- Security Reviewer
- Research Analyst
- Workflow Orchestrator
- Documentation Specialist
- Finance Analyst
- Customer Support Agent

A role icon should not represent one specific agent instance.

- Code Review
- Research

- Analysis
- Data Extraction
- Translation

- Summarization
- Testing
- Monitoring

# Team Icon

A team icon represents a stable approved group of AI agents.

Examples:

- Engineering Agent Team
- Security Review Team
- Research Team
- Incident Response Team
- Documentation Team

Teams should normally use:

- Role-family Icon
- Department Icon
- Approved Team Badge
- Text Label

A new independent team icon should be created only when long-term visual distinction is required.

Pool icons should identify the capability group, not a specific agent.


```text
ai-capability-{capability}
```

| Field | Description |
|------|-------------|
| Icon ID | Unique icon identifier |
| Role or Capability ID | Linked workforce identifier |
| System Name | Stable machine-readable name |
| Display Name | Human-readable role or capability |
| Type | Role, capability, team, or pool |
| Department Code | Owning or primary department |
| Description | Exact function represented |
| Primary Metaphor | Approved visual concept |
| Allowed Contexts | Approved usage contexts |
| Restricted Contexts | Prohibited usage contexts |
| Permission Sensitivity | Low, Medium, High, or Critical |
| Human Review Requirement | Yes, No, or Conditional |
| Variant | Outline, filled, or other |
| Default Size | Recommended size |
| RTL Behavior | Mirror or Fixed |
| Accessibility Label | Recommended label |
| Source Path | Master source location |
| Component Name | Code component |
| Version | Current version |
| Status | Approved, deprecated, or archived |
| Replacement | Replacement icon |
| Owner | Workforce or design owner |
| Reviewer | Design-system reviewer |
| License | Licensing status |

# Permission-sensitive Roles

Some role icons may represent sensitive functions.

Examples:

- Security Administration
- Access Governance
- Financial Approval
- Legal Review
- Production Deployment
- Data Deletion
- Incident Response
- Compliance Review

The icon does not grant the associated permission.

Actual authorization must come from:

- Role-based Access Control
- Policy Engine
- Approval Workflow
- Runtime Authorization
- Audit Record

---

# Authority Separation

Do not use icons to imply:

- Final legal authority
- Final financial authority
- Final hiring authority
- Unrestricted production access
- Human approval
- Compliance certification
- Security clearance

Visible role labels and permission context must remain accurate.

---

# Human Review Indicators

Some roles or capabilities may require human review.

Examples:

- Legal Decision Support
- Hiring Recommendation
- Financial Approval Support
- Security Exception Review
- Public Publication
- High-risk Automation

Human review requirements should be displayed through:

- Workflow Status
- Review Badge
- Policy Indicator
- Supporting Text

They must not be permanently embedded into the role icon.

---

# Agent Identity Separation

A specific agent profile should show:

```text
Agent Avatar

+

Agent Name

+

Primary Role Icon

+

Department

+

Runtime Status

+

Capabilities
```

Each element has a separate purpose.

---

# Runtime Status Separation

Possible runtime statuses include:

- Idle
- Running
- Waiting
- Paused
- Degraded
- Error
- Offline
- Retired

These must use `status-icons.md`.

Do not alter the role icon geometry or permanent color based on runtime state.

---

# Model Separation

AI workforce icons must not represent a specific underlying model unless the interface is explicitly showing model configuration.

Example:

```text
Research Agent Role Icon
```

should remain stable even when the agent switches between approved models.

Model identity belongs to model metadata, not role identity.

---

# Tool Separation

An agent role icon must not change whenever a tool is added or removed.

Tool access should be shown separately through:

- Tool List
- Capability Metadata
- Permission Panel
- Integration Badge

---

# Multi-role Agents

An agent may hold more than one approved role.

Recommended display:

- One Primary Role Icon
- Additional Role Labels
- Expandable Secondary Roles
- Capability List

Avoid displaying many icons in one compact row.

---

# Temporary Roles

Temporary AI roles may be created for:

- Incident Response
- Migration
- Audit
- Special Research
- Time-bound Campaign
- Client-specific Workflow

Temporary roles must include:

- Owner
- Purpose
- Start Date
- Review Date
- Expiry Date
- Permission Scope
- Archive Plan

A dedicated icon should be created only where reuse justifies it.

---

# Client-specific Roles

Client-specific icons must not become part of the shared enterprise package unless:

- The role is reusable.
- Licensing allows reuse.
- Confidentiality is preserved.
- Governance approves publication.
- Visual meaning is general enough.

Confidential client roles must remain in restricted packages.

# Unknown Role Handling

When an unknown role code is received:

- Use the approved generic AI role icon.
- Display the raw or resolved role name.
- Preserve the unknown code.
- Log the mapping issue.
- Do not guess a known role.
- Request registry synchronization.

---

# Unknown Capability Handling

When an unknown capability is received:

- Use the generic capability icon.
- Display the capability label.
- Preserve the raw capability code.
- Log the mapping issue.
- Avoid mapping it to an unrelated capability.

# Duplicate Prevention

Before creating a new icon:

- Search role registry.
- Search capability registry.
- Review department icons.
- Review action icons.
- Review status icons.
- Review product icons.
- Compare synonyms.
- Confirm role or capability meaning is distinct.
- Document why an existing icon is insufficient.

# Role Change Workflow

When a role changes:

- Confirm whether responsibility changed.
- Preserve the role code where meaning remains stable.
- Update visible name if needed.
- Review the icon metaphor.
- Review permissions.
- Update capability mappings.
- Update metadata.
- Update component registry.
- Record the change in the changelog.

A title change does not always require a new icon.

---

# Role Merge

When roles merge:

- Identify the surviving role.
- Preserve history.
- Review both role codes.
- Select one approved visual metaphor.
- Deprecate replaced icons.
- Migrate agent mappings.
- Update task routing.
- Update documentation.
- Record migration details.

---

# Role Split

When one role splits:

- Create separate role codes.
- Define clear responsibilities.
- Assign distinct icons where necessary.
- Update agent mappings.
- Update permissions.
- Update routing policies.
- Preserve the original role history.

---

# Capability Change

When capability meaning changes significantly:

- Create a new capability code.
- Create or approve a new icon.
- Deprecate the old capability.
- Update role mappings.
- Update workflow references.
- Publish migration guidance.

Do not reuse an existing capability code for a different meaning.

---

# Agent Retirement

When an agent retires:

- Keep the role icon active if the role still exists.
- Retire the agent avatar and identity record.
- Update runtime status.
- Preserve historical task records.
- Remove the agent from active routing.
- Archive the agent profile according to policy.

Role lifecycle and agent lifecycle are separate.

---

# Versioning

AI workforce icons follow semantic versioning.

| Change Type | Example | Meaning |
|-------------|---------|---------|
| Major | 2.0.0 | Significant metaphor or icon-system redesign |
| Minor | 1.1.0 | New variant, role, or supported size |
| Patch | 1.0.1 | Small optical or technical correction |

# Breaking Changes

Breaking changes may include:

- Role-code change
- Capability-code change
- System-name change
- Meaning reassignment
- Role and capability split
- Component removal
- Default variant change
- Registry mapping change
- Permission classification change

Breaking changes require migration documentation.

---

# Deprecation

When an AI workforce icon is deprecated:

- Mark it in the registry.
- Identify its replacement.
- Define migration deadline.
- Update role or capability mappings.
- Update workforce directories.
- Update workflow builders.
- Track remaining usage.
- Preserve source files.
- Preserve historical agent records.
- Record the change in `changelog.md`.

# Common Mistakes

Avoid:

- Using robot heads for every AI role.
- Using agent avatars as role icons.
- Using department icons as capability icons.
- Embedding runtime status into role artwork.
- Using action icons as capability icons without review.
- Creating one icon per individual agent.
- Inventing new role codes without governance.
- Inventing new capability codes without governance.
- Showing sensitive permissions through public metadata.
- Confusing review capability with approved status.
- Confusing orchestration with workflow status.
- Using model-provider logos as AI role icons.
- Using sparkles as the default AI metaphor.
- Keeping retired role mappings active.
- Publishing confidential roles in public packages.

# Best Practices

- Maintain stable role and capability codes.
- Separate role, capability, avatar, department, and runtime status.
- Use one shared icon family.
- Create icons for reusable roles and capabilities, not individual agents.
- Keep sensitive authority and permissions outside icon artwork.
- Use visible labels in workforce interfaces.
- Use one primary role icon per agent.
- Keep secondary capabilities in expandable metadata.
- Use approved generic fallbacks for unknown codes.
- Preserve historical mappings during workforce restructuring.
- Synchronize workforce registry, permissions, icons, components, workflows, and documentation.
- Archive deprecated icons instead of deleting them.
