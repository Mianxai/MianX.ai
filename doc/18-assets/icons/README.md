# Purpose

The `icons` folder serves as the official repository and governance center for all icons used throughout the Mianx.ai ecosystem.

It provides one controlled source of truth for icons used in:

- Web Applications
- Mobile Applications
- Desktop Applications
- AI Agent Interfaces
- Administrative Dashboards
- Developer Tools
- Documentation
- Marketing Material
- Presentations
- Workflow Systems
- Monitoring Platforms
- Enterprise Reports

Only approved icons registered in this repository should be used in production systems.

- Establish one centralized icon repository.

- Support AI-powered asset discovery.
- Preserve source files and version history.
- Enable automated validation and export.
- Maintain complete governance and auditability.

# Core Principle

Icons communicate function, state, category, or identity.

Every icon must be:

- Clear
- Consistent
- Recognizable
- Accessible
- Scalable
- Reusable
- Properly named
- Properly licensed
- Linked to an approved source
- Suitable for its intended context

Icons must not be treated as decoration where they communicate important meaning.

# Icon vs Logo

Icons and logos serve different purposes.

| Icon | Logo |
|------|------|
| Represents function or category | Represents brand or identity |
| Used inside interfaces | Used for official brand recognition |
| Usually simplified | May include symbol and wordmark |
| Part of the design system | Part of the brand system |
| May exist in large sets | Usually limited to approved variants |

An icon must not replace an official logo where brand identity is required.

---

# Icon vs Illustration

| Icon | Illustration |
|------|--------------|
| Small and functional | Larger and explanatory |
| Minimal detail | May contain detailed composition |
| Used in controls and navigation | Used in marketing and education |
| Consistent geometry | May use broader visual styles |
| Supports quick recognition | Supports storytelling |

Mianx.ai icons should communicate:

- Clarity
- Intelligence
- Simplicity

- Trust

# Visual Style

Official icons should generally be:

- Minimal
- Geometric
- Consistent
- Professional
- Grid-aligned
- Optically balanced
- Suitable for light and dark themes

Avoid:

- Mixed icon styles
- Unapproved cartoon graphics
- Excessive details
- Decorative shadows
- Random gradients
- Inconsistent stroke widths
- Photographic elements
- Emoji as production icons

---

# Icon Families

An icon family is a collection of icons sharing the same:

- Grid
- Stroke Width
- Corner Treatment
- Proportions
- Visual Weight
- Padding
- Optical Alignment
- Naming Standard

Icons from different visual families must not be mixed without approval.

---

# Primary Icon Family

The organization should maintain one primary icon family for core product interfaces.

The primary family should cover:

- Navigation
- Actions
- Status
- Files
- Communication
- Users
- Settings
- Security
- Data
- Workflows

---

# Secondary Icon Family

A secondary family may be approved for specialized contexts such as:

- Marketing
- Presentations
- Technical Diagrams
- Large Illustrative Icons
- Industry-specific Applications

The secondary family must not create inconsistency inside the primary product interface.

---

# Icon Grid

Every custom icon should be constructed on an approved grid.

Recommended base grids may include:

```text
16 × 16

20 × 20

24 × 24

32 × 32
```

The organization should select standard grids based on product requirements.

---

# Standard Icon Sizes

Recommended interface sizes:

| Size | Typical Usage |
|------|---------------|
| 12 px | Dense metadata or limited specialized use |
| 16 px | Compact controls and tables |
| 20 px | Standard buttons and inputs |
| 24 px | Navigation and general UI |
| 32 px | Cards and feature items |
| 48 px | Empty states and larger summaries |
| 64 px+ | Marketing or illustrative usage |

Icons must remain recognizable at their approved minimum size.

---

# Stroke System

Outline icons must use a consistent stroke system.

The system should define:

- Stroke Width
- Line Caps
- Line Joins
- Corner Radius
- Optical Adjustments
- Small-size Simplification

Stroke values must not be changed randomly in individual products.

---

# Filled and Outline Variants

Approved icon variants may include:

- Outline
- Filled
- Duotone, only if formally approved
- Monochrome
- Active State
- Selected State

Outline and filled variants must represent the same concept consistently.

---

# Optical Alignment

Icons must be optically balanced rather than relying only on mathematical centering.

Review:

- Visual center
- Edge weight
- Perceived size
- Vertical balance
- Horizontal balance
- Relationship with text
- Relationship with neighboring icons

---

# Padding

Each icon should include controlled internal padding.

Padding must:

- Preserve recognizability.
- Maintain family consistency.
- Prevent clipping.
- Support responsive scaling.
- Align with surrounding UI components.

---

# Color Usage

Icons should normally inherit color from the interface.

Example:

```css
.icon {
  color: currentColor;
}
```

This supports:

- Theme switching
- State changes
- Accessibility
- Reusability
- Design-token control

---

# Semantic Colors

Semantic icon colors may represent:

- Success
- Warning
- Error
- Information
- Disabled
- Active
- Selected

Color must not be the only method used to communicate critical meaning.

Use:

- Icon shape
- Text label
- Status description
- Accessible name

---

# Light and Dark Themes

Icons should function correctly in:

- Light Theme
- Dark Theme
- High-contrast Theme
- Printed Material
- Monochrome Context

Avoid creating separate icon artwork when design-token color changes are sufficient.

---

# Accessibility

Icons must support accessible interfaces.

Requirements include:

- Meaningful accessible labels where required.
- Sufficient contrast.
- Text labels for unfamiliar actions.
- Tooltips for ambiguous controls.
- Visible focus states for interactive controls.
- No color-only meaning.
- Appropriate target size for interactive icons.
- Decorative icons hidden from assistive technology.

---

# Decorative Icons

Decorative icons should not be announced by screen readers.

Example:

```html
<svg aria-hidden="true" focusable="false">
</svg>
```

---

# Meaningful Icons

Meaningful icons require an accessible name.

Example:

```html
<button aria-label="Delete task">
  <svg aria-hidden="true">
  </svg>
</button>
```

The button label provides the accessible meaning.

---

# Icon-only Buttons

Icon-only buttons must include:

- Accessible label
- Tooltip where useful
- Sufficient interactive target
- Keyboard support
- Focus indicator
- Disabled-state behavior

Do not rely on the icon alone for accessibility.

---

# Icon Naming

Every icon must have one clear semantic name.

Preferred naming examples:

```text
search

settings

user-add

file-download

task-complete

status-warning

notification-bell
```

Avoid names based only on appearance:

```text
magnifying-glass-2

round-shape

arrow-thing

new-icon-final
```

Semantic naming improves reuse and discoverability.

---

# Naming Convention

Use lowercase kebab-case.

General pattern:

```text
{category}-{concept}-{variant}
```

Examples:

```text
action-add.svg

action-delete.svg

navigation-home.svg

status-success-filled.svg

file-pdf.svg

department-engineering.svg

agent-orchestrator.svg
```

---

# Icon Identifier

Every governed icon should have a unique identifier.

Recommended pattern:

```text
ICON-{CATEGORY-CODE}-{CONCEPT-CODE}-{NUMBER}
```

Examples:

```text
ICON-ACTION-ADD-001

ICON-NAV-HOME-001

ICON-STATUS-ERROR-001

ICON-DEPT-ENG-001
```

---

# System Name

Each icon should include a stable machine-readable system name.

Example:

```text
System Name:
action-add

Display Name:
Add
```

The system name should not change simply because the visual design is updated.

---

# Icon Metadata

Each icon should track:

| Field | Description |
|------|-------------|
| Icon ID | Unique icon identifier |
| System Name | Machine-readable name |
| Display Name | Human-readable name |
| Category | Navigation, Action, Status, or other |
| Description | Intended meaning |
| Keywords | Search terms |
| Version | Icon version |
| Status | Draft, Approved, Deprecated, Archived |
| Source Type | Custom, Library, Partner, or External |
| Owner | Responsible team |
| Designer | Icon designer |
| Reviewer | Design-system reviewer |
| License | Licensing information |
| Source Path | Master source location |
| Export Path | Production export location |
| Replacement | Replacement icon if deprecated |
| Accessibility Notes | Usage and labeling guidance |

# SVG Requirements

Every SVG icon should:

- Use a valid view box.
- Scale correctly.
- Use clean paths.
- Avoid embedded scripts.
- Avoid unnecessary metadata.
- Avoid external dependencies.
- Support `currentColor` where appropriate.
- Remain visually consistent.
- Avoid excessive path complexity.
- Pass security validation.

# Custom Icon Request

A custom icon should be created only when:

- No approved icon exists.
- Existing icons do not communicate the concept.
- The requirement is reusable.
- The icon fits the enterprise visual language.
- The request has a defined owner.
- Design-system review is available.

---

# Custom Icon Request Information

Every request should include:

- Request ID
- Requested Concept
- Intended Meaning
- Intended Context
- Required Sizes
- Related Product
- Related Department
- Existing Alternatives Reviewed
- Accessibility Requirements
- Target Release
- Request Owner

---

# Duplicate Prevention

Before creating a new icon:

- Search by system name.
- Search by display name.
- Search by keyword.
- Review synonyms.
- Review related categories.
- Check existing external library.
- Check deprecated icons.
- Confirm the new icon is genuinely required.

# Icon Statuses

Approved statuses:

| Status | Meaning |
|--------|---------|
| Requested | Icon need has been submitted |
| Draft | Icon is under design |
| Under Review | Formal review is in progress |
| Approved | Ready for production |
| Published | Available in official library |
| Superseded | Replaced by a newer version |
| Deprecated | Must not be used for new work |
| Archived | Retained for historical reference |

# Versioning

Icons should follow semantic versioning.

| Change Type | Example | Meaning |
|-------------|---------|---------|
| Major | 2.0.0 | Meaning or visual language changes significantly |
| Minor | 1.1.0 | New variant or supported size added |
| Patch | 1.0.1 | Small path or export correction |

---

# Meaning Stability

An icon's meaning should remain stable across versions.

Example:

```text
action-delete
```

must continue to represent deletion.

A visual redesign must not change it into an archive action.

Where meaning changes, create a new icon ID.

---

# Deprecation

When an icon is deprecated:

- Mark it as deprecated.
- Identify its replacement.
- Define a migration deadline.
- Update the icon package.
- Warn developers and designers.
- Update usage documentation.
- Preserve the old icon for history.
- Track remaining usage.

# Common Mistakes

Avoid:

- Mixing outline and filled icons without a system.
- Using emoji as production UI icons.
- Naming icons only by shape.
- Creating duplicate icons for the same action.
- Using color as the only status signal.
- Using unfamiliar icon-only buttons without labels.
- Copying brand icons from image search.
- Using raster icons where scalable vectors are available.
- Publishing SVG files without security review.
- Changing an icon's meaning without creating a new ID.
- Keeping deprecated icons active indefinitely.
- Using multiple icon libraries in one interface.
- Storing icons without source files or metadata.

# Best Practices

- Maintain one primary icon family.
- Name icons according to meaning, not shape.
- Search before creating a new icon.

- Use `currentColor` where appropriate.
- Keep status color and icon shape meaningful.
- Preserve accessible labels for icon-only controls.
- Record every third-party license.
- Version source files and component packages.
- Automate SVG security and quality checks.
- Archive deprecated icons instead of deleting them.
- Keep design, development, metadata, and usage records synchronized.
