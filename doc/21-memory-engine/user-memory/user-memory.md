# Mianx.ai User Memory

> **This document defines the governed target-state model for User-specific
> Memory within the Mianx.ai Memory Engine.**
>
> **User Memory exists to preserve useful, authorized, purpose-bound
> continuity for a Human User without converting every interaction,
> observation, inference, personal detail, or behavioral signal into
> permanent Memory.**
>
> **A User statement does not automatically become User Memory.**
>
> **User Memory does not create enterprise truth, policy authority,
> Customer authority, Project authority, Agent authority, or permission to
> act.**
>
> **User identity, Customer, Tenant, Project, purpose, classification,
> provenance, lifecycle, privacy state, retention, and authorization must
> survive persistence, indexing, embedding, Vector projection, Graph
> projection, caching, summarization, retrieval, archival, deletion, and
> restore.**
>
> **User Memory must remain distinguishable from Customer Memory, Project
> Memory, Organization Memory, Agent Memory, Conversation Memory, and
> general Semantic Memory.**
>
> **The objective is not to remember everything about a User. The objective
> is to preserve the right information, about the right User, for the
> right purpose, inside the right scope, for the right duration.**
>
> **User Memory runtime capability, consent enforcement, privacy controls,
> cross-Tenant isolation, cross-Customer isolation, deletion propagation,
> derivative cleanup, export, restore reconciliation, monitoring,
> Evidence, and Production readiness remain `NOT_PROVEN` unless
> independently demonstrated.**

# 6. User Memory Objectives

User Memory should enable:

- continuity across authorized interactions;
- reduced unnecessary repetition;
- stable personalization;
- task and workflow continuation;
- appropriate preference reuse;
- improved User experience;
- authorized Human–AI collaboration;
- safer context retrieval;
- correction of inaccurate remembered information;
- governed forgetting and deletion;
- auditable Memory use.

---

# 7. Non-Goals

User Memory is not designed to:

- record every User action permanently;
- create unrestricted behavioral profiles;
- collect unrelated personal information;
- store credentials as ordinary Memory;
- infer sensitive personal characteristics without governance;
- bypass Customer or Tenant boundaries;
- bypass Project boundaries;
- bypass access control;
- create automated authority;
- create hidden policy;
- preserve deleted information indefinitely;
- replace authoritative identity systems;
- replace Customer systems of record;
- replace enterprise governance.

---

# 8. User as Memory Subject

Every User Memory record should identify the Human subject where required.

Conceptually:

```text
subject_user_id
```

must represent trusted identity rather than an unverified display name.

---

```text
DISPLAY NAME
≠

```

# 11. User ID Alone May Be Insufficient

The same Human User may operate in multiple Customers, Tenants,
Organizations, Projects, or roles.

Therefore:

```text
USER ID
ALONE
MAY NOT DEFINE
COMPLETE MEMORY SCOPE
```

---

# 12. Composite User Scope

```text
subject_user_id

customer_id

tenant_id

project_id

purpose

```

```text
USER X / TENANT A
≠
USER X / TENANT B
```

# 14. Same User Across Customers

```text
USER X / CUSTOMER A
≠
USER X / CUSTOMER B
```

by default.

# 15. Same User Across Projects

```text
USER X / PROJECT A
≠
USER X / PROJECT B
```

when Project scope materially affects meaning or authorization.

# 16. Same User Across Roles

A User may hold different roles in different contexts.

Example:

```text
USER X
=
ADMIN IN PROJECT A

USER X
=
VIEWER IN PROJECT B
```

User Memory retrieval must not use the higher role as universal authority.

# 41. User Memory and Episodic Memory

User-specific events may be represented as Episodic Memory.

# 42. User Memory and Long-Term Memory

Long-term User Memory should contain only information that remains useful,
authorized, proportionate, and eligible under retention policy.

# 44. User Memory and Working Memory

Working Memory may contain active User context needed during execution.

Working state should not automatically persist indefinitely.

verified:


rather than broadening access.
