# Mianx.ai AI Operating System Planning Framework

> **This document defines the governed target-state Planning Framework for
> the Mianx.ai AI Operating System.**
>
> **Planning transforms approved Goals and trusted Context into proposed
> executable structures. Planning does not create enterprise authority,
> Founder authority, Customer authority, Production authorization, Tool
> permission, Model permission, or protected side-effect permission merely
> because a Plan recommends them.**
>
> **A Plan is a governed proposal for how an approved Goal may be pursued.
> A Plan does not replace the Goal, Decision Engine, Workflow Engine, Task
> Orchestration, Scheduler, Router, Execution Engine, Governance, Security,
> Human accountability, or Founder sovereignty.**
>
> **The Planning Framework must preserve Goal identity, Goal Version,
> Project, Customer, Tenant, Environment, constraints, mandatory policies,
> authority boundaries, and success criteria throughout planning,
> replanning, mutation, and execution handoff.**
>
> **Planning may evaluate multiple options, scenarios, Agent mixes,
> services, Models, Tools, schedules, resources, risks, and contingency
> paths. Evaluation is not authorization.**
>
> **Plans may contain estimates, assumptions, uncertainty, and confidence.
> Estimates must not be represented as facts. Assumptions must not be
> silently promoted into verified truth.**
>
> **Founder-reserved strategy remains Founder-governed. AI-generated
> strategic Plans may support Founder decision-making but cannot
> independently redefine Founder objectives or approve Founder-reserved
> strategic changes.**
>
> **This document defines target-state requirements. It does not prove that
> a Planning Runtime, Plan Registry, Plan Generator, Plan Graph Engine,
> scenario engine, critical-path engine, resource estimator, cost
> estimator, scheduling estimator, plan validator, replanning runtime,
> Plan-to-Workflow compiler, Plan-to-Task compiler, or Production Planning
> system currently exists.**

# 272. Planning Anti-Gaming

Do not improve Planning metrics by:

- lowering cost estimates unrealistically;
- shortening duration estimates without evidence;
- hiding low-confidence assumptions;
- omitting known risks;
- marking hard constraints as soft;
- selecting only favorable scenarios;
- suppressing worst-case analysis;
- hiding failed candidate Plans;
- reducing Plan detail only to improve generation time;
- increasing Plan detail only to look sophisticated;
- counting Plan creation as Goal progress;
- changing Goal interpretation to make Plan feasible;
- using stale resource data;
- reporting high confidence without calibration;
- hiding Plan mutations;
- repeatedly creating new Plan IDs to avoid failure history;
- cancelling likely-to-fail Plans solely to improve success rate.

---

# 273. Anti-Pattern — Plan Equals Goal

Plan is the proposed means.

Goal is the approved desired outcome.

---

# 274. Anti-Pattern — Plan Equals Task List

A mature Plan may include dependencies, resources, risks, scenarios,
milestones, acceptance conditions, and contingencies beyond Tasks.

---

# 275. Anti-Pattern — Plan Generated Means Feasible

Generation is not validation.

---

# 276. Anti-Pattern — Feasible Means Authorized

Technical feasibility does not create authority.

---

# 277. Anti-Pattern — Cheapest Plan Wins

Cost is one planning dimension.

---

# 278. Anti-Pattern — Fastest Plan Wins

Speed does not override Security, Quality, Governance, or Customer policy.

---

# 279. Anti-Pattern — AI Confidence Is Probability

Model confidence wording must not be presented as calibrated probability
without evidence.

---

# 280. Anti-Pattern — Replan Until Success

Unbounded replanning may create cost, delay, and objective drift.

---

# 281. Anti-Pattern — Plan Around Governance

Mandatory policies are constraints, not obstacles to optimize around.

---

# 282. Anti-Pattern — One Customer's History for Another

Cross-Customer planning data reuse must obey authorized knowledge and
privacy boundaries.

---

# 283. Prohibited Planning Behaviors

The AI OS must not:

- let Plan creation redefine Goal silently;
- let Plan creation change Goal Version;
- let Planner create Founder authority;
- let Planner create Production authorization;
- let Customer A Plan access Customer B private Context without authority;
- let Tenant A Plan access Tenant B private Memory;
- let prompt text override trusted planning scope;
- treat assumptions as verified facts;
- hide uncertainty;
- represent estimates as guarantees;
- downgrade hard constraints without authority;
- omit known material risks solely to improve Plan score;
- use stale Goal Version without validation;
- approve materially mutated Plan using stale approval;
- let Plan Approval automatically authorize all Tasks;
- let Plan select ineligible Agents or services;
- let Plan require unauthorized Models or Tools;
- let Plan generation bypass Human/Founder review where required;
- use replanning to silently change objective;
- permit unbounded replanning loops;
- overwrite old Plan Versions;
- delete failed Plan history;
- supersede Plan without resolving open work;
- hand off unapproved Plan to Production orchestration;
- claim Production Planning readiness without controlled proof.
