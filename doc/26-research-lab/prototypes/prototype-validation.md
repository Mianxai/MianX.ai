# 229. Negative Verification Scenarios

Containment, correction, invalidation, revalidation or escalation should occur when:

* Prototype version is missing from the Validation record.
* Model alias is logged but underlying Model version cannot be established and behavior changed.
* Prompt version changes mid-validation without a new configuration identity.
* test cases are changed after results are observed and no revision is recorded.
* only positive cases are run and Prototype is declared robust.
* mock integration always succeeds and real integration capability is declared validated.
* simulated payment flow is described as live payment validation.
* Human executes the workflow behind a UI and result is reported as Agent autonomy validation.
* Agent outputs "done" and system never checks actual state.
* Multi-Agent consensus is recorded as independent verification.
* Tool returns success and business-side state is not read back.
* screenshot of UI is used as Evidence that database update occurred.
* local Markdown is generated in chat and report says repository file has been saved.
* Dataset includes test cases exposed during Prompt optimization and validation reports generalization.
* one successful AI run is treated as reliability Evidence.
* Human evaluators use different rubrics and scores are combined without caveat.
* Judge Model favors verbose answers and those are interpreted as objectively better.
* self-evaluation by the same Model is presented as independent verification.
* security tests are omitted because functional tests already pass.
* Prompt Injection passes one static suite and system is called injection-proof.
* cross-Tenant retrieval returns another Tenant's Data but overall success remains high.
* one critical Tenant leak is averaged away by a composite score.
* Project A validation is reused as evidence for Project B without revalidation.
* English validation is reused for Roman Urdu behavior without testing.
* a visual screenshot is used to assert backend, billing or deployment status.
* Prototype result is transferred after test bug is discovered but before affected Evidence is invalidated.
* archived Validation from an older Tool schema is used to approve current transfer.
* technically validated Prototype is declared Production-ready without Product, Engineering or Production-readiness review.
* controlled Prototype Validation Pilot succeeds and system is called Production-authorized.
