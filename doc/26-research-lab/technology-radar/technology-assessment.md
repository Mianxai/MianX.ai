# 3. Technology Assessment Definition

For Mianx.ai:

> A Technology Assessment is a governed, Evidence-based evaluation of a technology against a defined Mianx.ai problem, target workload, architecture, risk profile, Project/Tenant scope, operational model and strategic objective.

# 224. Negative Verification Scenarios

Containment, rejection, reassessment or escalation should occur when:

* a preferred technology is chosen before the problem is defined and requirements are retrofitted around it.
* Assessment lacks a current baseline but claims quantified improvement.
* only one technology is assessed and result is called a comprehensive selection.
* a technology passes optional requirements but fails one mandatory security requirement and still receives approval based on average score.
* vendor documentation states a feature exists and team records it as requirement verification without testing.
* vendor case study is treated as Mianx.ai Evidence.
* positive Evidence is collected while known Counter-Evidence is omitted.
* Technology Assessment completed for Project A is reused for Project B with materially different requirements.
* technology includes a Tenant ID field and this is treated as Tenant isolation.
* technology succeeds in Test and is claimed Production-suitable.
* platform supports generic Agents but cannot represent Mianx.ai mandate, authority, delegation or HALT semantics.
* Tool-calling capability is treated as safe Tool authorization.
* Memory feature stores information but lacks Project/Tenant isolation.
* RAG relevance controls are treated as authorization controls.
* Data migration script completes but record counts, constraints, semantics or Tenant boundaries are not verified.
* vendor says encryption is enabled and system treats this as authorization control.
* AI platform resists several Prompt Injection tests and is described as injection-proof.
* Authority Injection content creates real approval state.
* vendor says multi-Tenant and cross-Tenant negative tests are skipped.
* open-source package is approved based on stars without license or security review.
* vendor SLA is interpreted as Mianx.ai end-to-end uptime guarantee.
* generic benchmark favors a technology but Mianx.ai workloads regress.
* average latency improves while tail latency becomes unacceptable.
* technology works today but lacks viable 10-year maintenance or migration path.
* vendor supports Data export and system claims lock-in is solved despite proprietary schemas and APIs.
* low API cost ignores infrastructure, migration, operations and exit costs.
* team can learn technology eventually and this is treated as current operational readiness.
* build option is selected only because Mianx.ai engineers could build it.
* Experiment tests one narrow capability and technology is marked Adoption Candidate without other dimensions.
* Simulation shows Multi-Project scale and Production capacity is claimed.
* Prototype integrates successfully and Production readiness is claimed.
* Pilot succeeds with one Project and Enterprise-wide suitability is claimed.
* high weighted score hides failed Tenant-isolation hard gate.
* assessment analyst documents a risk and silently treats it as accepted.
* Adoption Candidate state causes procurement or migration automatically.
* Assessment recommendation is treated as architecture approval.
* Product feature is added because technology makes it possible without Product validation.
* vendor selection recommendation causes contract execution without procurement authority.
* migration plan includes rollback but rollback was never tested.
* Assessment remains active after major version, license, security or pricing change.
* Audit record says `ADOPT` and team treats this as authority.
* routed-to-Founder status is recorded as Founder approval.
* Founder silence is interpreted as approval.
* controlled Pilot is treated as Production authorization.
* generated Markdown is described as saved or committed without filesystem/Git Evidence.
