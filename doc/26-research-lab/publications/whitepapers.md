# 265. Negative Verification Scenarios

Containment, correction, withdrawal, retraction or escalation should occur when:

* thesis is written as established fact before Evidence is collected.
* public Whitepaper calls itself peer reviewed when only internal review occurred.
* conceptual architecture diagram is presented as deployed Mianx.ai architecture.
* target-state AI Workforce capabilities are described as current Runtime capabilities without Evidence.
* five articles all derived from one vendor press release are presented as five independent confirmations.
* vendor Benchmark is presented as independent Mianx.ai Benchmark.
* citation is attached to a claim but the source does not support the stated conclusion.
* outdated market forecast is reused as current market size without checking freshness.
* competitor lacks public documentation and Whitepaper states competitor lacks the capability.
* one Model Benchmark score is used to claim end-to-end enterprise superiority.
* one Prompt pattern improves a test set and is called universally optimal.
* Multi-Agent consensus is described as verified truth.
* Agent says task completed and Whitepaper describes verified business outcome.
* Tool reports success and Whitepaper claims real side effect without state verification.
* hypothetical customer scenario is written as if it were a real customer deployment.
* composite customer example is attributed to a named real customer.
* one positive Case Study is generalized across all industries.
* large TAM is translated directly into projected Mianx.ai revenue without market-share assumptions.
* forecast is presented as guaranteed roadmap outcome.
* Whitepaper recommends a technology and Engineering treats it as approved architecture.
* Whitepaper target Roadmap is presented as Founder-approved committed Roadmap without approval Evidence.
* external publication includes Tenant Data that was authorized only for internal Research.
* public architecture diagram exposes security-sensitive details.
* unpublished patentable method is disclosed before appropriate IP review.
* brand review approves document and team skips technical verification.
* customer-approved Case Study content is reused in a Whitepaper without checking whether Whitepaper use is authorized.
* internal Whitepaper approval is reused as public approval.
* version 2 changes major claims but version 1 approval is reused.
* Whitepaper becomes stale after major Model/market/regulatory change but continues to be distributed as current.
* retracted Whitepaper remains linked from sales material.
* document says Founder approved because it was routed to Founder.
* generated Markdown is described as saved to repository without filesystem Evidence.
* controlled Whitepaper publication Pilot succeeds and publication system is described as Production-authorized.
