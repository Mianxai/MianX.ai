# 233. Negative Verification Scenarios

Containment, correction, withdrawal, retraction or escalation should occur when:

* target-state architecture diagram is described as current deployed architecture.
* report says component is implemented because a design document exists.
* code sample in report is treated as proof file exists in repository.
* local file is visible in VS Code and report claims remote GitHub repository contains it without remote verification.
* commit hash exists locally and report claims push succeeded without remote Evidence.
* build succeeds but Runtime endpoint is broken and report says system is verified.
* deployment command returns success but report claims Production health without post-deployment checks.
* synthetic Dataset result is presented as real-customer performance.
* Model alias changes behind provider endpoint but report combines results as one fixed Model version.
* Prompt changes during Benchmark and results are reported as one configuration.
* Agent outputs "task complete" and report records business workflow success without state verification.
* Multi-Agent agreement is written as independent verification.
* Tool call returns success but source system shows no side effect.
* Benchmark set appears in Prompt examples and report still calls score generalization.
* average latency is low while critical P99 is hidden.
* one cross-Tenant leak occurs but composite quality score remains high and report marks system healthy.
* security testing covers only known Prompt Injection strings and report claims injection-proof.
* no security incident occurs during test and report says system is secure.
* Pilot runs successfully for limited users and report calls architecture Production-scale.
* estimated token cost is reported as total system cost while Human review and infrastructure are omitted.
* technical finding is promoted into enterprise architecture decision without decision authority.
* technical recommendation is described as approved technology.
* report omits failed experiments that contradict preferred architecture.
* internal peer review is described as external scientific peer review.
* internal security-cleared report is published externally without IP/legal review.
* report version is materially updated but old approval reused.
* report later becomes stale after major Model or architecture change and remains used as current decision Evidence.
* invalid Benchmark methodology is discovered and report is not corrected/retracted.
* report claims Founder approval because it was routed to Founder.
* generated report is described as saved to filesystem without filesystem Evidence.
* a controlled Technical Report publication Pilot succeeds and publication system is described as Production-authorized.
